# Building Atrium (M0 state)

`build/args.gn` sets `proprietary_codecs = true` and `ffmpeg_branding = "Chrome"` so H.264/AAC playback (YouTube, most of the web) works - the default free-codecs-only build fails with `MEDIA_ERR_SRC_NOT_SUPPORTED` on H.264 sources.

It also sets `generate_about_credits = true`. The default is `is_official_build`, which served a placeholder at `chrome://credits` instead of the real third-party notices. True runs `tools/licenses/licenses.py` over the tree and bakes the result into `resources.pak`, so the page is generated by the build and readable offline. Reachable in the UI at Settings > About > Open source licenses.

## HTML chrome surfaces

The sidebar always renders as HTML (`chrome://atrium.top-chrome/sidebar`) -
there is no switch to turn it off. Everything else - pill, peek, command bar,
settings, foyer - is rebuilt in HTML too; `make run` alone starts
Atrium with all of it.

Anything below that describes a SwiftUI surface, `libAtriumUI.dylib` or
`ATRIUM_UI_DYLIB` is history now that H4 rebuilt those surfaces. It is kept
because it records what the surfaces DID, which is what the rebuilds matched.

`make run` rebuilds the Chromium side and launches. A no-op rebuild costs ~11s
and leaves the app's cdhash unchanged, so it does not re-trigger the Safe
Storage prompt.

`make dev-install` builds a static app in `out/atrium-static`, copies it to
`~/Applications/Atrium.app` and starts it with `open`. Use it when a macOS
permission such as Local Network matters: a terminal launch makes macOS check
the terminal app, not Atrium. The first static build takes about 2.5 hours.

## Generating for Linux (H3)

`gn gen` runs for `target_os = "linux"`. The build does
not, yet - that is H3.7 and H3.8.

One prerequisite the checkout does not ship:

```
python3 build/linux/sysroot_scripts/install-sysroot.py --arch=arm64
```

Without it, `gn gen` stops at a `Missing sysroot` assertion in
`build/config/sysroot.gni` and never reaches any Atrium file - so a failure
there says nothing about the Atrium sources.

`make linux-verify` runs the whole thing (~10s, no build):

| Command | Does |
|---|---|
| `make linux-verify` | Drift guard: `gn gen` for `target_os=linux`, then assert no Objective-C or Swift is in the Linux atrium source list |
| `make linux-verify-selftest` | Prove the guard can fail - a dirty source list must exit non-zero (no gn, no checkout) |

Current output: 37691 targets, 31 atrium sources in `//chrome/browser/ui:ui`.

By hand, if you want the raw numbers:

```
mkdir -p out/linuxgen
printf 'target_os = "linux"\nis_debug = false\nis_component_build = true\n' > out/linuxgen/args.gn
gn gen out/linuxgen
gn desc out/linuxgen //chrome/browser/ui:ui sources | grep -c atrium/
```

`gn gen` succeeding is not the check that matters. GN does not compile
anything, so it will hand a `.mm` file to a Linux toolchain without complaint
and the mistake stays invisible until H3.7/H3.8 produce a Linux builder. What
`linux-verify` adds is the extension check on that list.

One source fails it today: `atrium/atrium_settings_menu_hook.mm` imports
`<Cocoa/Cocoa.h>` and its own header sits in the `is_mac` arm, but the `.mm`
sits in the portable arm. It is marked in the guard's
`KNOWN_NON_PORTABLE` list and prints as `EXPECTED FAILURE`, the same posture VM
scenarios use for `cannot_pass`. A NEW `.mm` fails the gate; so does deleting
the file from the Linux list without deleting its mark. Moving that one line
into the `is_mac` arm is the fix, and it needs `make patches-regen`.

## Run Atrium

    make build
    ./build/scripts/run-atrium.sh

`run-atrium.sh` sources `build/scripts/env.sh` and launches the `out/atrium/Atrium.app`
binary with a dedicated profile at
`~/Library/Application Support/Atrium/Chromium`. This supersedes the
content_shell run instructions below.

One step used to come first: `build/build-ui.sh`, which built the Swift dylib,
and `build/inject-dylib.sh`, which put it in the bundle and re-signed. Both went
when the Swift package was removed, along with `make ui`, `make test`, `make abi-verify` and
`make abi-sync`. The keychain re-prompt those steps caused went with them - the
bundle is now only re-signed when the icon changes.

The last built dylib is not deleted, only set aside, at
`$SRC/out/atrium/atrium-pre-cut/libAtriumUI.dylib`. A VM scenario can still be
pointed at a copy of it with `ATRIUM_DYLIB_REMOTE` when the question is whether
the cut changed a behaviour. The source is recoverable from the `last-swift`
tag in both repos.

**The launch detaches into its own session.** A SIGTERM to the
process group that invoked `run-atrium.sh` (e.g. an agent tool call that times
out) no longer reaches Atrium - Chromium's own signal handler would otherwise
treat that as an ordinary quit, which looked exactly like a spontaneous exit.
One side effect: Ctrl-C in the launching terminal no longer stops Atrium
either. Kill it by PID instead (`pgrep -x Atrium`, then `kill <pid>`) - never
`pkill -x Atrium` on a shared host, which cannot tell your instance from
someone else's. `make run-detached` launches the same way but backgrounds the
`make` recipe itself, returning the terminal immediately; `build/scripts/verify-detach-survival.sh`
(`make verify-detach`) is the regression guard that proves Atrium keeps
running unattended.

### Dock/Finder launch

`run-atrium.sh` is not the only way in. `PreSandboxStartup`
(`chrome_main_delegate.cc`, see `atrium::ApplyDefaultLaunchSwitches()`) defaults
`--user-data-dir`, `--no-first-run` and `--no-default-browser-check`, so
double-clicking `Atrium.app` from the Dock or Finder behaves the same as
`run-atrium.sh`. A CLI flag always overrides the default.

### Shared bundle across worktrees

`out/atrium/Atrium.app` is ONE bundle shared by every worktree building against
the same `$SRC` - whichever session built last silently wins, regardless of
which branch a tester believes they are running.

This got smaller with the cut: the provenance stamp that `inject-dylib.sh` wrote
into `Info.plist` went with it, because what it identified was the dylib. What
remains shared is the Chromium build itself, and `build/VERSION` plus
`make patches-verify` already say whether that matches the tree. A per-worktree
bundle is still open.

### Reset to factory defaults

Clears Atrium's persisted state so the next launch is a clean first run - the
fastest way to re-test onboarding, migrations, or anything state-dependent.

    make reset FLAGS=--dry-run      # preview only; changes nothing
    make reset                      # refuses without FLAGS=--yes
    make reset FLAGS=--yes          # full reset
    make reset-stores FLAGS=--yes   # keep Chromium profiles/logins

| Target | Moves aside | Keeps |
|---|---|---|
| `reset` | the whole `Atrium/` dir, including `Chromium/` | nothing |
| `reset-stores` | `spaces.json`, `spaces.json.bak`, `themes.json`, `settings.json`, `hotkeys.json`, `routing.json`, `favicons/` | `Chromium/` (profiles, logins, cookies) |

Nothing is deleted: everything moves to
`~/Library/Application Support/Atrium.reset-backup-<timestamp>/`. Restore by
moving that directory's contents back.

Quit Atrium first - the script refuses to run while the app is up. A
non-interactive call without `--yes` falls back to a dry run rather than
guessing.

## Spaces (M2b)

- State file: `~/Library/Application Support/Atrium/spaces.json` (independent of
  the Chromium profile dir; survives `--user-data-dir` overrides).
- First run (no file present): one default space, "Personal", profile `Default`,
  no saved tabs - the active space opens `about:blank`.
- Reset to defaults: quit Atrium, delete `spaces.json` (and its `.bak` if
  present), relaunch.

## Multi-window (M2c)

- `Cmd+N` opens a new window on the current space; the same space can be open
  in more than one window at once.
- Activating a tab in a window moves it there if it was showing in another
  window of the same profile (Arc-style tab handoff, not a duplicate).
- Closing a window does not destroy its tabs - they go cold (persisted, not
  rendered) until reactivated in another window; closing the last window quits
  Atrium.
- Window-exclusion plumbing (hidden windows kept out of Cmd+~/Window
  menu/Mission Control) is in-process-only: it works within a single Chromium
  process but is not propagated across the remote_cocoa app-shim boundary, so
  it has no effect for out-of-process app shims.

## Command bar (M4)

Every fresh tab gets the prompt. `Cmd+T` creates a new blank tab (exactly
like the pre-M4 behavior) AND opens a centered command palette
(Arc/Raycast-style) over it; the sidebar's "+ New Tab" button opens the
palette too (without creating a tab - `open_command_bar` op).
Accepting a palette action fills the Cmd+T tab in place (fresh-blank
consumption); dismissing without accepting leaves the blank tab (Chrome
NTP-style). App launch auto-opens the palette once the startup window has
shown its initial tab - same UX as `Cmd+N`. Third optional ABI group,
`command_bar_connected_`, resolved the same AND-gated way as
`spaces_connected_` - CORE and spaces are unaffected if it fails to resolve.

- Ops (appended to `AtriumHostOps` after `set_backdrop_tint`): `command_bar_query(host, text)`,
  `command_bar_stop(host)`, `set_default_search_engine(host, keyword)`,
  `open_command_bar(host)`, `command_bar_dismiss(host)`.
- Exports: `AtriumCreateCommandBar(host, ops, slotID) -> NSView*` (+1 retained),
  `AtriumOnCommandBarResults(host, json)`, `AtriumOpenCommandBar(host)`,
  `AtriumCopySearchEnginesJSON() -> char*` (strdup, caller frees),
  `AtriumOnDefaultSearchChanged(host, searchURLTemplate, user_chosen)` -
  `user_chosen` distinguishes a persisted user selection from
  `TemplateURLService`'s built-in fallback default, so the first-run engine
  picker knows whether to reappear.
- Standalone optional additions (resolved on their own, never AND-ed into the
  group - an older dylib keeps the full palette without them):
  `command_bar_delete_match(host, index)` op,
  `AtriumOnCommandBarPass(host, json)` export,
  `AtriumOpenCommandBarWithReason(host, reason)` export.

### Match payload

Each match carries, on top of `type`/`relevance`/`url`/`contents`/
`description`/`is_search`:

| Key | Meaning |
|---|---|
| `index` | Position in the C++ `AutocompleteResult` - the `command_bar_delete_match` handle |
| `deletable` | `AutocompleteMatch::SupportsDeletion()` |
| `inline_autocompletion` | Tail Chromium would append after the typed prefix |
| `fill_into_edit` | What accepting should put in the edit field |
| `allowed_to_be_default_match` | Whether it may be preselected |
| `contents_class` / `description_class` | `{offset, length, style}` ranges; UTF-16 code units, `style` is Chromium's bitmask (URL 1, MATCH 2, DIM 4) |
| `stripped_destination_url` | Canonical dedup key; falls back to `url` when empty |
| `image_url` / `icon_url` | Provider artwork; key absent when there is none |

### Streamed passes

`AtriumOnCommandBarPass` carries `{"generation": int, "final": bool,
"matches": [...]}` for EVERY pass, not just the final one, so the first
keystrokes paint real results. `generation` is bumped per
`command_bar_query`; Swift's `CommandBarTypingGate` drops older generations
and holds a provisional pass while the user is mid-keystroke. Exactly one of
`AtriumOnCommandBarPass` / `AtriumOnCommandBarResults` fires per pass - a
dylib without the former still gets final-only results, exactly as before.

### Open reason

`AtriumOpenCommandBarWithReason` adds WHY the palette is opening: `0` new tab
(Cmd+T, unchanged) or `1` edit current URL (Cmd+L - prefills the active tab's
URL fully selected, suppresses switch-to-tab rows, Escape restores). Values
are ABI, append only. Per-window, so two windows can differ.

### Query field keys

The query field is an `NSTextField` (`CommandBarQueryField`), not SwiftUI's
`TextField`: only a real field exposes the caret and selection that inline
autocomplete, Left/Right acceptance, and undo need. Every binding below is
field-local - it applies while the palette has focus and nothing else.

- `Return`: Commit the highlighted row
- `Escape`: Close the palette
- `Up` / `Down`, `Ctrl+P` / `Ctrl+N`: Move the selection
- `Tab`: Scope the search to the highlighted suggestion's site
- `Right` / `End` / `Ctrl+E`: Accept the inline completion
- `Left`: Dismiss the inline completion
- `Backspace` / `Fn+Delete`: Dismiss the inline completion
- `Backspace` on an empty query: Close the palette
- `Shift+Fn+Delete`: Forget the highlighted history suggestion
- `Ctrl+C`: Copy the highlighted suggestion's URL; the typed text for a search row
- `Cmd+Z` / `Cmd+Shift+Z`: Undo / redo the query

While a scope is locked (see below):

- `Return`: Search the scoped engine for the typed terms
- `Escape`: Leave the scope and restore the pre-`Tab` text
- `Backspace` on an empty query: Leave the scope

Collisions: none of the above appear in `ReservedHotkeys`, the `hotkeys.json`
defaults, or Chromium's `global_keyboard_shortcuts_mac.mm`. `Ctrl+C` was chosen
over `Cmd+Shift+C` because that table binds Cmd+Shift+C and Cmd+Opt+C to
Inspect Elements and Cmd+Ctrl+C to Add Tab To Group; the only control-only
entries are Ctrl+PgDn/PgUp. Plain `Tab` is free too - `ReservedHotkeys` reserves
only `Ctrl+Tab` / `Ctrl+Shift+Tab` - and is claimed through `insertTab:` and
swallowed unconditionally, since passing it back to AppKit would move first
responder off the query field. `Cmd+Z`/`Cmd+Shift+Z`/`Ctrl+C` are claimed
through an `NSEvent` local monitor scoped to the focused field - the main menu
matches Cmd chords before the field editor ever sees them. Undo history is the
model's own (`CommandBarQueryHistory`), over the typed query only, so undoing
never restores a completion suffix the user did not type.

### Scoped quick search

`Tab` on a suggestion whose site is a searchable engine locks the palette to
that engine: the prompt clears, a chip names the engine, typing plus `Return`
searches it, and `Escape` (or `Backspace` on an empty query) restores the exact
pre-`Tab` text. Only Results rows offer a scope - a Switch-to-Tab row is an
existing tab, not a site. While scoped the palette asks the AutocompleteController
nothing, so no suggestion, inline completion, or in-flight pass can contradict
the chip. A scoped accept is deliberately not recorded in the learned-selection
store: the query is search terms, not a destination, so the record could only
ever mislead the same characters typed unscoped.

Engines resolve in one order:

| Source | When |
|---|---|
| The match's own `keyword` / `engine_name` / `search_url_template` | Whenever C++ carries them (no build emits them yet) |
| `CommandBarScopedEngineRegistry`, keyed on the match's host | Otherwise |

Fallback contract (command_bar group absent - core/spaces-only dylib):

| Surface | With command bar | Fallback |
|---|---|---|
| `Cmd+T` | Creates a blank tab AND opens the palette over it | Instant `about:blank` tab only, no palette (M1/M2a behavior, unchanged) |
| App launch | Auto-opens the palette after the startup tab shows | No palette |
| Sidebar "+ New Tab" | Opens the palette | Instant `about:blank` tab |
| Pill search fallback | Uses the pushed search-URL template | Hardcoded DuckDuckGo |

Per-host warm `AutocompleteController`: one `AutocompleteBridge` per
(host, profile) (`atrium_autocomplete_bridge.{h,mm}`), constructed at host
registration rather than on first keystroke so the async `InMemoryURLIndex`
rebuild has a head start. It also observes `TemplateURLService` to push the
default search engine's URL template to Swift at registration and on every
later change.

Palette widget: a frameless, activatable, translucent child `views::Widget`
(a borderless child NSWindow on Mac, same primitive as the omnibox popup)
hosts the Swift-built palette `NSView` via `NativeViewHost`. SwiftUI draws
both the dim scrim and the centered card; the widget itself is just a
transparent full-parent-bounds surface with no scrim/centering logic. The
widget is positioned with the parent's FULL screen rect (its bounds are
screen coordinates - it is a top-level widget, so parent-relative (0,0)
would anchor it to the desktop corner) and re-applies those bounds on every
parent move/resize via a `WidgetObserver` on the parent. The card is
draggable by its non-interactive chrome (padding/edges/footer), clamped to
stay fully visible; the position lasts for the palette instance's session
and resets to centered on relaunch (not persisted). The card's background is
a real `NSVisualEffectView` pinned to `state = .active` (`.popover` material,
`.behindWindow` blending), not SwiftUI's own `.regularMaterial` - the palette
always renders in its active appearance regardless of the widget's real
key/main status, which churns on real hardware in ways a VM does not
reproduce (`--vmodule=atrium_command_bar_widget=2` logs both halves of every
activation transition for diagnosis). Dragging survives a gesture restart
(SwiftUI silently cancelling and re-recognizing the `DragGesture` mid-drag on
activation churn) by re-priming the drag base on every distinct
`DragGesture.Value.startLocation`, not on a `isDraggingCard` check that a
cancelled-not-ended gesture never resets.

## Tab switching (Arc M3)

Two independent tab-cycle gestures, both driven by the standalone optional
`AtriumOnTabCycle(host, axis, direction)` export (axis 0 = recency, axis 1 =
sidebar order).

- **Ctrl+Tab / Ctrl+Shift+Tab** — instant recency (MRU) cycle over the last 5
  activated tabs, scoped to the ACTIVE SPACE only (never switches spaces). No
  overlay: the moving sidebar selection highlight is the feedback. Rapid
  repeated presses walk deeper into the recency list; the walk resets after a
  quiet gap or any non-cycle activation. **Not rebindable** this milestone -
  the chord is matched literally in `AtriumCommandDispatcherDelegate::
  prePerformKeyEquivalent` and reserved from `hotkeys.json` (both C++
  `NativeHotkeyMap::ParseCombo` and Swift `ReservedHotkeys` reject it, so a
  bound action can never be silently shadowed).
- **Cmd+Opt+Down / Cmd+Opt+Up** — WYSIWYG sidebar-order cycle: walks the tab
  rows exactly as the sidebar lists them (pinned, expanded-folder members,
  ungrouped), skipping hidden rows; a cold row materializes on landing.
  Rebindable as the native actions `nextTab` (Cmd+Opt+Down) / `previousTab`
  (Cmd+Opt+Up) via `hotkeys.json`, same channel as `openCommandBar`/
  `toggleSidebar`.
- **Cmd+L** — opens the command bar with the active tab's URL prefilled and
  fully selected, so typing replaces it; Escape leaves the tab untouched.
  Rebindable as the native action `editCurrentURL`. Claimed from stock
  `IDC_FOCUS_LOCATION` in the raw-event hook, which runs before Chromium's
  accelerator lookup; rebinding it away returns Cmd+L to that stock meaning.
- **Seam choice** — Ctrl+Tab, Cmd+Opt+Left/Right, and Ctrl+PgDn/PgUp all map to
  the SAME `IDC_SELECT_NEXT_TAB`/`IDC_SELECT_PREVIOUS_TAB` commands, and the
  IDC intercept (`AtriumBrowserWindow`) receives only an int32 command id - no
  `NSEvent` - so it cannot tell them apart. The reroute therefore matches the
  raw chord in `prePerformKeyEquivalent` instead, firing ONLY on
  Ctrl+Tab/Ctrl+Shift+Tab and leaving Cmd+Opt+Left/Right (space cycle) and
  Ctrl+PgDn/PgUp (stock strip cycle) untouched.
- **Degradation** — an old dylib without `AtriumOnTabCycle` leaves Ctrl+Tab at
  stock strip-cycling and Cmd+Opt+Down/Up unbound; no crash.

## Code signing (keychain)

Atrium stores its cookie/password encryption key in the macOS keychain under `Atrium Safe Storage`. Access is gated on the app's code-signing identity. An ad-hoc signature pins that grant to the binary hash, which changes every build, so macOS re-prompts on every launch.

`build/scripts/setup-signing-cert.sh` creates a stable self-signed `Atrium Dev` identity (idempotent; run automatically by `build-shell.sh`). Override the name with `ATRIUM_SIGN_IDENTITY`; if the identity is missing, the build falls back to ad-hoc and warns.

**Dev launches use the real keychain by default.** `run-atrium.sh` no longer passes `--use-mock-keychain` unless asked, so a dev launch touches `Atrium Safe Storage` like a Dock/Finder launch always did - and **can prompt**, once after each code-changing build, until Developer ID signing lands. Why it prompts at all: the Safe Storage item's ACL is partitioned by cdhash, because a self-signed identity carries no Team ID, so every code-changing build produces a new cdhash that is not yet in the partition list (see below).

**The terminal grant was removed.** `run-atrium.sh` used to run `build/scripts/authorize-keychain.sh` before launch, which asked for the login password on the tty in order to prevent the GUI Safe Storage prompt. It did not prevent it - Atrium asked for the password anyway - so the grant cost one prompt and saved none. Paying two prompts is worse than paying one, so the call is gone.

`build/scripts/authorize-keychain.sh` still exists and can be run by hand if the partition list needs updating. `ATRIUM_KEYCHAIN_KEEP_ALL=1` appends instead of replacing (adds ~25s); replacing is the default because the list had grown to 79 entries, one per past **Always Allow**, all pointing at builds that no longer exist.

The real fix is Developer ID signing: a Team ID makes the partition `teamid:`, which is stable across builds, instead of the per-build cdhash a self-signed identity forces. Until then, expect one Safe Storage prompt after a code-changing build.

Set `ATRIUM_MOCK_KEYCHAIN=1` to opt back into the old mock-keychain behavior (no prompt). Real costs:
- OSCrypt derives its key from the keychain, so the mock keychain means a different key - **cookies and saved passwords written under the real key do not decrypt, and dev launches start logged out**.
- Switching modes between launches (mock <-> real) makes Chromium's tracked-preference enforcement silently wipe every protected pref that has a value - this is what made the search-engine picker reappear. Pick one mode per profile and stick to it.

`ATRIUM_REAL_KEYCHAIN=1` is now a no-op (the default already is the real keychain). Harmless if still set in a shell profile, but drop it.

One-time steps after adopting this:

- First build may show `codesign wants to sign using key ...` - click **Always Allow** once (the login keychain password blocks setting this non-interactively).
- Renaming the keychain item regenerates the encryption key, so saved passwords/cookies reset once (re-login to sites). Bundle id also changed to `org.atrium.Atrium`, resetting app-level permission grants (notifications, mic) once.

### Still prompting every launch?

Expected with the default real keychain (and always true for Dock/Finder launches): one prompt after each code-changing build, none in between. More than that - or a prompt while `ATRIUM_MOCK_KEYCHAIN=1` is set - means something below is wrong.

**A stable signing identity is not enough, and a clean designated requirement does not prove anything.** The ACL on `Atrium Safe Storage` is partitioned by **cdhash**, separately from the designated requirement, because a self-signed identity carries no Team ID and macOS falls back to cdhash when there is no stable `teamid:` to key on. Every build that changes the app's code produces a new cdhash, which is not in the partition list, so the next launch prompts and the granted hash is appended. securityd says so directly:

```
[com.apple.securityd:integrity] ACL partition mismatch: client cdhash:708e361c... ACL (
    "cdhash:55b59cd9...", "cdhash:667ac861...", ... )
[com.apple.securityd:kcacl] displaying keychain prompt for .../Atrium.app(83546)
```

That is the whole of the "random" re-prompt: **once after each code-changing build, never in between.** The real fix is a Developer ID signature, whose `teamid:` partition survives every rebuild.

Diagnosing a prompt, in order:

1. **Read securityd rather than guessing.** `log show --last 1h --predicate 'process == "securityd"' | grep -E "partition mismatch|displaying keychain prompt"` names the client and the reason. `log show --last 1h --predicate 'process == "SecurityAgent"' | grep "server port"` gives one line per prompt actually shown, which is the cheapest way to correlate prompts with builds.
2. **Unsealed code in the process.** Loading a dylib the app's signature doesn't cover breaks the process's dynamic code identity, and a broken identity matches no ACL. `run-atrium.sh` injects the freshly built `libAtriumUI.dylib` into the bundle and re-signs, rather than pointing `ATRIUM_UI_DYLIB` at `.build/release`. Exporting that variable by hand re-breaks the grant for as long as it is set.
3. **A stale ACL entry.** A trusted-application entry is a snapshot of the app's identity taken when it was added. One added while cause 2 was in effect still *displays* as `Atrium.app` while matching nothing, so re-clicking Always Allow only rewrites a dead entry. Fix in Keychain Access: `Atrium Safe Storage` > Access Control > remove the `Atrium.app` entry, re-add it from `$SRC/out/atrium/Atrium.app`, Save Changes. Non-destructive - the stored key is untouched, so saved logins survive.

Note what does *not* diagnose this: `codesign -d -r- $SRC/out/atrium/Atrium.app` reads `identifier "org.atrium.Atrium" and certificate leaf = H"..."` with no `cdhash` term - i.e. a rebuild-proof designated requirement - on a build that prompts anyway. The DR and the partition list are different mechanisms.

### WebAuthn Touch ID cannot work on the dev build

Sites offering a platform authenticator get `touch_id_context.mm:89 Touch ID authenticator unavailable because keychain-access-group entitlement is missing or incorrect`. This is not a dev-loop bug to patch - it is three independent, stacking gaps, and none of them close without release signing:

1. **The entitlement is never generated for this build.** `chrome/BUILD.gn` only appends `app-entitlements-chrome.plist` (the file carrying the `keychain-access-groups` array, including the `.webauthn` entry `touch_id_context.mm` checks for) `if (is_chrome_branded && include_branded_entitlements)`. Atrium builds with plain `chrome/app/theme/chromium/BRANDING`, i.e. `is_chrome_branded = false` - so the base `app-entitlements.plist` (camera/mic/bluetooth/usb/location/photos, all inert since Atrium isn't sandboxed) is all GN ever produces, regardless of signing identity or Team ID. Chromium's own `include_branded_entitlements` comment says why: "certain entitlements are tied to the official Google code signing identity" - confirming this class of entitlement is designed to require Google's real identity, not a stand-in.
2. **The expected value depends on a Team ID that does not exist.** `ChromeWebAuthenticationDelegate::TouchIdAuthenticatorConfigForProfile()` builds the expected group as `MAC_TEAM_IDENTIFIER_STRING "." MAC_BUNDLE_IDENTIFIER_STRING ".webauthn"`. `MAC_TEAM_ID` in the BRANDING file is empty (no paid Apple Developer Program membership yet), which is exactly why the run log's "Expected value" has a leading dot: `.org.atrium.Atrium.webauthn`. Even granting that entitlement string to the binary would not make it functional: macOS validates a `keychain-access-groups` claim against the code signature's real, Apple-issued Team ID, and a self-signed identity carries none (`codesign -dvvv` on the current build reads `TeamIdentifier=not set`) - the same reason the unrelated "Atrium Safe Storage" default-group item already had to fall back to cdhash-based ACL partitioning instead of a stable `teamid:` partition (see above). There is no equivalent fallback for a named, shared access group; an unsigned-for-Team-ID process can be granted its own implicit identity, not a shared one.
3. **The dev re-sign step strips entitlements outright.** `build/scripts/env.sh`'s `atrium_codesign()` - run by `build/scripts/inject-icns.sh` and `build/scripts/build-shell.sh` on every dev build - is `codesign --force --sign "$ATRIUM_SIGN_IDENTITY" "$bundle"` with no `--entitlements` flag. (`build/inject-dylib.sh` no longer exists, the Swift dylib build went with it, but the same flat re-sign call is still what runs today.) Re-signing without `--entitlements` does not preserve whatever the initial ninja build produced; it replaces the signature with zero entitlements. Verified directly: `codesign -d --entitlements - $SRC/out/atrium/Atrium.app` on the current build returns nothing at all, not even the inert base-plist keys.

**Verdict:** Touch ID as a WebAuthn platform authenticator cannot be made to work on the self-signed `Atrium Dev` build, by entitlements-file editing or otherwise - there is no dev-build workaround, only the release signing path. Closing this needs all of: (a) build wiring so Atrium's entitlements include the webauthn `keychain-access-groups` array without piggybacking on Google's `is_chrome_branded` gate, (b) a real paid Apple Developer Program Team ID in `MAC_TEAM_ID`, (c) actual Developer ID Application signing (not self-signed) so the OS can cryptographically validate that Team ID, and (d) the dev re-sign step preserving entitlements rather than discarding them (or the notarized release path not going through it at all). The release signing plan covers identity, hardened runtime and notarization only. Add (a), the entitlements-file wiring, when scoping that work.

Touch ID itself remains unverified end-to-end: no machine with a Touch ID sensor was exercised against a real WebAuthn test site as part of this investigation (the Tart probe VM has no Touch ID sensor either), and the finding above is that no build exists yet worth testing that way.

### Release signing: Developer ID, hardened runtime, notarization

**There is no dylib-injection conflict.** An earlier plan assumed Atrium loads `libAtriumUI.dylib` by injection (`build/inject-dylib.sh`) and that the hardened runtime's library validation would refuse it unless co-signed or granted `com.apple.security.cs.disable-library-validation`. Commit `c0a35ffe` (2026-08-09) deleted `swift/`, `build/inject-dylib.sh`, `build/build-ui.sh`, and the dylib build entirely - the sidebar is now drawn by the Rust core, not injected via a Swift dylib. Verified directly: `grep -n dylib build/scripts/run-atrium.sh build/scripts/build-shell.sh Makefile` returns nothing, `swift/` does not exist in the working tree. There is nothing left to co-sign or grant an entitlement to. **No library-validation trade-off is needed**: no third-party or unsigned dylib is loaded, so library validation stays fully enabled with no exception carved out.

**A second, unrelated dylib population does exist and needs no entitlement.** `build/args.gn` sets `is_component_build = true` for the fast dev loop, which produces ~525 loose first-party `lib*.dylib` files resolved via rpath (`build/scripts/vm.sh:165`). These are Chromium's own translation units, signed by the same identity as the app in a release build - the hardened runtime's library validation allows same-Team-ID dylibs by design, no entitlement needed. A release build must set `is_component_build = false` (Chromium's own signing docs require this - see below), which removes this dylib population by linking everything statically. This is not a decision to make; it is the standard release configuration Chromium ships.

**Chromium already ships a complete signing/entitlements/notarization pipeline; Atrium's build does not use it.** `chrome/installer/mac/signing/` (`parts.py`, `model.py`, `config.py`) plus `chrome/installer/mac/sign_chrome.py` define exactly which bundle parts get the hardened runtime, which get JIT instead of library validation, and which entitlements file each one carries. Today `build/scripts/build-shell.sh` and `build/scripts/env.sh`'s `atrium_codesign()` bypass all of this: one flat `codesign --force --sign "$ATRIUM_SIGN_IDENTITY" "$bundle"` on the outer `.app`, no `--options runtime`, no `--entitlements`, no `--deep`, and the Helper apps and `chrome_crashpad_handler` are never signed individually. That is fine for local dev (Gatekeeper is never consulted) and is exactly why release signing is unmet today. The cause is that nobody wired it up, not a dylib conflict.

**What each part needs, read from `chrome/installer/mac/signing/parts.py` and the entitlements files it references (all confirmed present in `~/chromium-atrium/src/chrome/app/`):**

| Bundle part | `codesign --options` | Entitlements file | Why |
|---|---|---|---|
| `Atrium.app` (outer) | `restrict,library,runtime,kill` (`FULL_HARDENED_RUNTIME_OPTIONS`) | `app-entitlements.plist` | Full hardened runtime; no JIT needed at this layer |
| `Framework.framework` | (none - it's a dylib, options are meaningless here) | none | Signed as a library, not an executable |
| `chrome_crashpad_handler` | `restrict,library,runtime,kill` | none | No JIT, no relaxation needed |
| `... Helper.app` (main/network/utility) | `restrict,library,runtime,kill` | none | No JIT |
| `... Helper (Renderer).app` | `restrict,runtime,kill` (**no** `library`) | `helper-renderer-entitlements.plist` (`com.apple.security.cs.allow-jit`) | V8's JIT needs `allow-jit`; Chromium's comment in `parts.py` is explicit that `LIBRARY_VALIDATION` is "incompatible with the JIT entitlement" for this helper - so it is left off rather than disabled after the fact |
| `... Helper (GPU).app` | `restrict,runtime,kill` (**no** `library`) | `helper-gpu-entitlements.plist` (`com.apple.security.cs.allow-jit`) | Same JIT/library-validation trade-off, for the GPU process's shader JIT |
| `... Helper (Alerts).app`, `app_mode_loader`, `web_app_shortcut_copier` | `restrict,library,runtime,kill` | none | No JIT |
| `libEGL.dylib`, `libGLESv2.dylib`, `libvk_swiftshader.dylib`, `libvulkan.dylib` (ANGLE/SwiftShader, built from the same source tree) | (loose dylibs, signed individually) | none | Loaded by the GPU process via the framework's rpath; same-identity signing satisfies library validation - no `disable-library-validation` entitlement anywhere in this pipeline |

The security posture Chromium chose is therefore: **JIT and library validation never coexist on one process** - the two renderer/GPU helpers give up library validation (they can `dlopen` anything with a valid signature, not only same-Team-ID code) in exchange for `allow-jit`, and every other part keeps full library validation with no JIT. Nothing in this pipeline uses `com.apple.security.cs.disable-library-validation` or `com.apple.security.cs.allow-unsigned-executable-memory` - `allow-jit` alone covers V8/GPU-shader JIT under the hardened runtime. Atrium inherits this trade-off unmodified once it signs with this pipeline; no Atrium-specific relaxation is needed unless a future Atrium-authored helper also needs JIT.

## VM probe environment

Agent-driven probes (CGEvent clicks, AppleScript, fullscreen windows,
screencapture) steal focus from the host desktop. `build/scripts/vm.sh` runs them
inside a headless Tart VM (`atrium-probe`) instead - builds stay on the host,
only run+probe moves to the VM.

**Permissions:** none to grant. Cirrus base images pre-seed TCC for CI -
verified 2026-07-07 over SSH with no manual grant: `screencapture` produces a
real frame, `System Events` key events post, and AX window queries against
Atrium succeed. If a future base image tightens TCC, fall back to a
graphical session (`TART_HOME=/Volumes/AtriumBuild/tart tart run atrium-probe`,
login `admin`/`admin`), grant Accessibility + Screen Recording in System
Settings, then re-run `./build/scripts/vm.sh snapshot`.

**The clean image must carry the probe tools pre-built.** `build/vm-tools/*.swift`
are compiled inside the VM, and a freshly compiled binary is a new binary to
TCC: its first ScreenCaptureKit call silently returns no frames. `vm-scenario.sh`
skips the rebuild when `tools/src/<tool>.swift` in the VM matches the host's
sha256, which only works if the clean image already holds those sources and
their granted binaries. Before `./build/scripts/vm.sh snapshot`, stage the current
sources to `~/atrium-probe/tools/src/`, compile each with `swiftc -O`, and run
`rapidcap` a few times so it holds a working grant. `CLEAN_VM=...`
overrides which image `restore` clones.

**The window-picker consent alert is dismissed per run, not seeded.** macOS 26
periodically re-asks for screen recording over an existing grant, naming the SSH
session `rapidcap` rides over: "com.apple.sshd-session is requesting to bypass
the system private window picker". It is system-modal, so while it is up macOS
swallows every synthetic click and scroll and a scenario fails on missing vlog
gates rather than on behaviour. The snapshot cannot pre-answer it - the alert is
not the `kTCCServiceScreenCapture` row (already `auth_value=2`, and untouched
when the alert is answered), and answering one writes no file a restore would
carry. So `vm-scenario.sh` lets the warm-up capture trigger it, finds it by
comparing the alert's app icon against a measured colour, and clicks Allow,
logging `harness: dismissed the window picker consent`. A second check runs
immediately before the first action and fails the run loudly if it is still up.

**Agent workflow** (no graphics, no focus stealing):

```
./build/scripts/vm.sh restore   # reset to the $CLEAN_VM snapshot (atrium-probe-clean-v3)
./build/scripts/vm.sh start     # boot headless, wait for SSH
./build/scripts/vm.sh deploy    # rsync Atrium.app + component dylibs + build/vm-fixtures/
./build/scripts/vm.sh run-atrium
./build/scripts/vm.sh shell     # ssh in to run probes (CGEvent/AppleScript/screencapture)
./build/scripts/vm.sh stop
```

`make vm-start` / `vm-stop` / `vm-deploy` / `vm-shell` wrap the same script.

### Running a browser_tests gtest case in the VM

`browser_tests` (InProcessBrowserTest) hard-requires the real Chromium source
tree at a fixed relative depth from its own directory
(`chrome::DIR_TEST_DATA`) and resolves the top-level `Atrium Framework.framework`
bundle relative to itself too. A copied deploy into `~/atrium-probe` satisfies
neither, and the 121GB checkout does not fit the VM's 50GB disk to copy. So
`run-gtest` boots the VM with the live checkout virtiofs-mounted read-only
(`tart run --dir=src:$SRC:ro`) and runs the binary in place from the mount -
that directory is the exact `out/atrium` ninja built on the host, so the
framework bundle is already sitting next to the binary, no rsync needed. It
restores the VM to its normal no-mount headless state afterward.

```
./build/scripts/vm.sh run-gtest browser_tests --gtest_filter=Foo.Bar
make vm-run-gtest BIN=browser_tests FILTER=Foo.Bar
```

**A second-profile window must be closed before the test ends, not left for
fixture teardown.** "Multi-window" alone is not the constraint:
`AtriumAdoptTabIntoLittleWindowBrowserTest` (two windows, same profile) passes
cleanly through ordinary end-of-test teardown. `CloseBrowserSynchronously()`
mid-test is also not the constraint on its own: that call times out (30s) in
this VM's headless (`--no-graphics`) mode, a separate, earlier-documented
problem. A test isolated the actual trigger by taking
`AtriumSidebarDropBrowserTest.DifferentWorkspaceAsksFirstAndDoesNotMove` -
which creates a second real `Profile` plus a `CreateLittleWindow` on it via
`BrowserController::RouteSidebarDrop`'s ask-first (no-move) branch, and
reliably hits the `FATAL Check failed` at
`content/browser/renderer_host/browser_compositor_view_mac.mm:379`
(`new_parent_ui_layer->GetCompositor()`) - and changing exactly one thing:
closing that second-profile window itself, during the test, via
`chrome::CloseWindow()` (posted, non-blocking) followed by
`ui_test_utils::WaitForBrowserToClose()`, before the test body returns. With
that one change (`AtriumMultiProfileTeardownBrowserTest.
AskFirstBranchClosedBeforeTeardown_Passes`,
`chrome/browser/ui/atrium/atrium_multi_profile_teardown_browsertest.cc`) the
test passes; without it, the original crashes deterministically. Leaving a
second-profile window open until `InProcessBrowserTest`'s own fixture
teardown has to close it alongside `browser()`'s window is the trigger for
this test shape - `AtriumMoveLittleTabToSpaceBrowserTest.CrossProfileReopensURL`
already followed the same rule by construction: its production
code path (`MoveLittleTabToSpace`) closes the little window itself via the
same `chrome::CloseWindow()` + `WaitForBrowserToClose()` pair before the test
ends. A minimal reproduction that skipped `RouteSidebarDrop` entirely (a bare
second Profile + `CreateLittleWindow`, real navigation, left open for
teardown) did NOT crash, so the trigger is not "any second-profile window left
open" in isolation - it is specific to this handler's shape, and the fix
(close it explicitly before the test ends) is the one verified, actionable
takeaway. The untried next step for a test that genuinely needs the window to
stay open through fixture teardown (deliberately not attempted, since it
would put a visible window on the host desktop) is a VM booted with a real
attached display instead of `--no-graphics`.

**A freshly-created ordinary window needs a tab before it is closed.**
`chrome::ScopedTabbedBrowserDisplayer`'s fallback path calls
`Browser::Create()` directly (`scoped_tabbed_browser_displayer.cc`) with no
tab - real callers add one immediately via `Navigate()`.
`AtriumLittleWindowFindTabbedBrowserBrowserTest.
DisplayerOpensANewBrowserInsteadOfTheLittleWindow` closed that
window straight away and hung forever in `WaitForBrowserToClose()`, on both
the buggy and the fixed binary: the window's pill/sidebar HTML surface
(`BuildHtmlArm`) was still loading and its close never signalled
`GlobalBrowserCollection`. Giving it a tab (`chrome::AddTabAt`) and waiting
for that tab's load (`content::WaitForLoadStop`) before `chrome::CloseWindow()`
made the test resolve in ~7s. This is a different rule from the
`CloseBrowserSynchronously` one above - it applies to any ordinary
(non-little) Atrium window created bare in a test, not to little/chromeless
windows or to the compositor FATAL.

Assumptions: `tart` installed (`brew install cirruslabs/cli/tart`); base image
`ghcr.io/cirruslabs/macos-tahoe-base` (guest 26.5 <= host major); `TART_HOME`
defaults to `/Volumes/AtriumBuild/tart` since the host boot disk runs
near-full. SSH uses a dedicated keypair at `$TART_HOME/atrium-probe-key`,
authorized in the guest via `tart exec` on each `start`. The component build's
loose dylibs (~785 MB) deploy next to the .app; full deploy is ~930 MB,
incremental rsync is fast.

### Is the app even alive?

```
make vm-lifetime          # one number, about four seconds
```

Launch, poll, report - no scenario, no fixture, no assertions. When the question
is whether the app is running at all, every one of those is a way for the
answer to arrive as somebody else's failed assertion.

Written after a UI-thread crash killed the app three seconds after launch and
spent an hour looking like a broken scenario harness. It said `GONE after ~3s`
straight away, and `STILL ALIVE after 148s` once the cause was reverted. On a
GONE it points at `/tmp/atrium-run.log`, where a `FATAL` line names the reason.

Reach for it first whenever scenarios fail in a way that suggests nothing
happened - missing windows, gates that time out, captures of an empty screen.

### Which file holds your change

`Atrium.app/Contents/MacOS/Atrium` is a **52 KB stub**. In this component build
the code lives in `libchrome_dll.dylib`, and `vm.sh deploy` rsyncs that dylib
beside the .app - so a target you relinked ships to the VM whether or not the
bundle's executable changed.

Checking the bundle's mtime to decide whether your change is in the running
build is checking a proxy. On 2026-08-09 that cost an hour: a
`base::ReadFileToString` on the UI thread went out in a `chrome/browser/ui:ui`
relink, killed the app three seconds after launch, and was blamed on the
scenario harness three times because the .app's executable was hours old.

```
ls -l "$SRC/out/atrium/libchrome_dll.dylib"     # the file that matters
```

Cheaper rule: if you built any `//chrome` target this session, assume it ships.
Building `unit_tests` does not relink it; building a `source_set` that
`//chrome/browser/ui:ui` depends on does.

`swift test` is genuinely independent - it builds into `.build/debug`, while
the deployed dylib is `.build/release/libAtriumUI.dylib`.

## VM probe fidelity rules

A hands-on review re-marked five items `[!]` after the VM probe suite had
passed them (batch-4053). The rules
below were extracted from that gap analysis and validated by the rework round
that followed it - keep applying them, don't re-litigate the retrospective.

| Rule | Rationale |
|---|---|
| Capture a frame sequence for any motion claim (`build/vm-tools/rapidcap.swift` - burst capture via `SCStream`, `rapidcap <outdir> <durationMs> <fps> [x y moveDelayMs]`; for drags, the `cgevent` `rawdown`/`rawdragged`/`rawup` primitives) | A forked `screencapture` per frame costs ~150-190ms - longer than most UI animations, so it always misses the transition |
| Build a side-by-side, same-scale composite for any "X should match Y" claim | Reviewer and user must judge the SAME artifact; an isolated measurement of X doesn't prove it matches Y |
| Mark physical-input/feel/scale-dependent rows needs-hardware, never PASS | Synthetic CGEvents can't reproduce third-party input mangling; VM display scale doesn't transfer to real hardware; feel isn't provable by log or unit test |
| Inventory every surface a user-visible complaint could mean before fixing | Item 38's first pass fixed the in-app PNGs' alpha while the actual complaint was the Dock `.icns` |
| Hard-fail inconclusive rows; never downgrade one to a note inside a PASS | A row rationalized as "VM artifact" is how item 48 shipped as fixed the first time |
| Reviewers pixel-diff evidence (raw pixels, not PNG file hash) and code-trace probe claims | Encoder noise makes hashes differ on identical pixels; a byte-for-byte diff caught item 58's retracted frame claim (the two "before/after" frames were identical) |
| Evidence class must match the claim type | Pixel claims need matched-scale screenshots; input claims need a real-device row; feel/motion claims need a frame sequence or an explicit needs-hardware deferral |
| One VM session at a time - the controller serializes `atrium-probe` access (or staggers streams that need it) | Two incidents this round of sibling streams clobbering each other's VM sessions (foreign `--user-data-dir` processes, external `CloseAllBrowsersAndQuit` killing in-flight probes) cost most of one stream's wall clock |

## VM scenario runner

`build/scripts/vm-scenario.sh` turns the manual probing above into a repeatable,
asserting regression harness. A scenario is a declarative JSON spec under
`build/scenarios/`; the runner restores the VM to a clean snapshot, deploys the
current build, stages the probe tools, launches Atrium on a chosen startup
space, runs input actions, evaluates assertions, and always tears down.

```bash
make vm-scenario SCENARIO=presenter-startup   # run one (needs a live VM)
make vm-scenario-all                          # run all; non-zero exit on any FAIL
make vm-scenario-list                         # list scenarios
./build/scripts/vm-scenario.sh --validate presenter-startup   # parse-only, no VM
```

Prerequisite (once): `make build` for a current build, and
`./build/scripts/vm.sh snapshot` to capture the clean state the runner restores to.

Spec format (`build/scenarios/<name>.json`):

| Key | Meaning |
|---|---|
| `fixture` | spaces JSON staged as `ATRIUM_SPACES_FILE` |
| `themes` | optional themes JSON staged as `ATRIUM_THEMES_FILE` (a space is themed when this keys its UUID) |
| `startup_space` | space UUID Atrium launches on - patched into the fixture's `activeSpaceID` (the presenter bug is startup-space-dependent) |
| `actions[]` | `settle` / `capture` (rapidcap burst) / `key` (cgevent combo, e.g. `cmd+2` = go to space 2) / `resize` / `drag` / `scroll` (cgevent phase-based trackpad scroll with real `.began`/`.changed`/`.ended` phases and momentum decay) / `scroll_during_capture` (same, backgrounded rapidcap burst across the gesture) / `crash_renderer` (SIGSEGV to one named renderer - see below) / `relaunch` (stop the app and start it again without restaging - see below) |
| `assertions[]` | `ax_window_count` / `theme_changed` / `pixels_changed` (see below) / `region_stable` / `resize_applied` / `quit` / `vlog` / `vlog_absent` / `vlog_after` / `file_contains` (see below) |
| `cannot_pass` | optional; a short reason this scenario cannot pass on the current build, plus the baseline numbers it was measured at. Set only where a run failed the scenario AND the source says why. The runner prints it, so a red line reads as expected rather than as a regression. Delete the field when the reason stops being true - a scenario that starts passing with one still set is the signal to remove it |
| `teardown_assertions[]` | optional; the same types, evaluated after the harness stops the app and re-pulls the run log. The only way to gate on a line the app writes on its way out - a final flush, the sidebar's last push as the strip empties. Anything in `assertions[]` reads a log pulled before the quit, and a `wait_vlog` action would time out on a line that does not exist yet. `quit` is rejected here - the app is already gone |

Assertion helpers (`build/scenarios/lib/asserts.sh`) and the tools they drive:

| Assertion | How it is evaluated | Fidelity guard |
|---|---|---|
| `ax_window_count` | `axresize <app> count` (real windows above `min_area`, filtering child widgets), retried to absorb switch settle | The presenter/window-jump signature is a second ordered NSWindow - a clean cross-profile switch keeps exactly one |
| `theme_changed` | host `pixcmp diff` on a backdrop region of the last before/after frames - raw decoded pixels, mean-colour delta + region variance | Byte-identical frames exit 3 = FAKE (never a pass); no PNG file-hash compares |
| `pixels_changed` | host `pixcmp moved` on the same kind of region, then `lib/moved_outcome.py` - counts the CORRESPONDING PIXELS that differ, rather than comparing the two region means (see below) | A `min_changed_pct` outside (0, 100] is refused by both the validator and the grader; a region under 400 px is refused as too small to carry a percentage; byte-identical frames are still a FAKE |
| `resize_applied` | `axresize <app> size` then `get`, checked within tolerance | AX resize, no mouse travel, so it probes layout not hover |
| `quit` | `cgevent keypress 12 cmd` (Cmd+Q), then poll `pgrep` until gone | PASS only when no process remains |
| `file_contains` | `cat` the staged file out of the VM, then `lib/file_value.py` compares one JSON path against the expected value | A staged fixture that already held the value is a FAIL, not a pass - it cannot tell a write from no write |

Artifacts (frames, AX dumps, run log, `results.log`) land under
`build/vm-fixtures/results/<name>-<timestamp>/`. The `key` action can name a
`vlog` regex to cite the concrete action VLOG from the run log, per the
never-outcome-only rule above. The `theme_changed` region is in frame PIXEL
space (2x retina) and may need tuning against a real before-frame if it
overlaps opaque web content.

The probe tools compile inside the VM (`cgevent`/`axresize`/`rapidcap` need the
VM's AX/ScreenCaptureKit/TCC grants); `pixcmp` is host-compiled pure image math.

### Crashing a renderer

`{"type": "crash_renderer", "target": "chrome"}` sends SIGSEGV to exactly one
renderer. Written for the chrome surfaces have no address bar, so
`chrome://crash` is unreachable, and `pkill -x Atrium` takes the whole app.

| Target | Resolves to |
|---|---|
| `chrome` | the shared chrome-layer renderer - sidebar, command bar, pill, foyer and settings all live in this one process |
| `web` | the renderer showing an http(s) page |
| `browser` | REFUSED - killing the browser process is the `quit` assertion's job |

Selection runs on the host in `build/scenarios/lib/pick_renderer.py`, from two
signals that must agree: Chromium's `--top-chrome-webui` switch on the process,
and a route that process actually committed in the run log. The switch alone
also matches a spare renderer, which hosts no surface. No match, or more than
one, is a FAIL - never a guess.

The browser is refused three times over: `parse.py` rejects the target name at
validation so no VM boots, the picker refuses any pid running the browser
binary, and the runner re-reads the target's own command line from the live
process before signalling it. `make crash-pick-test` covers the first two
without a VM.

The action grades itself, because the pid is not knowable when a spec is
written: the target must be gone, the browser process must still be up, and the
renderers that vanished must be exactly the one it named. `results.log` records
the pid, the before/after renderer sets, and the browser's `Task died,
PID=<pid>` line.

`crash-chrome-renderer` is the worked scenario. Both its log gates are
`vlog_after`, and the second anchors on `Received signal 11` rather than on the
sidebar commit: anchored at the commit it matched a utility process that exited
during startup, five seconds before anything crashed. Ordering is what pins a
gate to the right death when the pid cannot be named.

### Proving a file survived a relaunch

Every other assertion here is satisfied by a REPAINT: a surface that draws the
new value and writes nothing passes the window count, the pixel compare and the
log gate alike. Persistence needs two pieces that did not exist before.

`{"type": "file_contains", "file": "spaces", "path": "appState.activeSpaceID",
"value": "2222..."}` reads a staged file back out of the VM.

| Choice | Why |
|---|---|
| a JSON path, not a substring | `"schemaVersion": 3` is a substring of a file whose value is 30; `true` matches any bool in the object |
| compared as JSON, not as text | `true` is not `"true"` and 1 is not `"1"` - the confusions a serializer round trip produces |
| not a whole-file match | the writer is serde and the fixture is hand-written, so spacing and key order differ on every real run |
| the staged copy is part of the check | if the fixture already held the value, the assertion passes against a build with no writer - so that is a FAIL |

`file` names a staged file (`spaces` / `settings` / `themes` / `hotkeys` /
`routing`), never a raw remote path: a path the harness never staged has no
host-side copy to compare against. `parse.py` rejects a name the scenario stages
none of. `make file-value-test` covers the grader without a VM.

`{"type": "relaunch"}` stops the app with Cmd+Q and calls `launch_atrium` again.
NOT RESTAGING IS THE POINT - `stage_fixtures` re-copies every fixture out of the
repo, so chaining two scenarios could never ask whether a write survived. Cmd+Q
rather than a kill, because a write may only flush on the way out
(`atrium_core_save()` in `PostMainMessageLoopRun`).

The second launch TRUNCATES `/tmp/atrium-run.log`, so `pull_run_log` keeps each
closed segment and assembles them with `atrium harness: launch <n> begins here`
between. Both launches write the same lines, so a read-back gate must be a
`vlog_after` anchored on that marker; a plain `vlog` is green for a second
launch that read nothing. `wait_vlog` and `vlog_cite` still grep the live log
inside the VM, so after a relaunch they see the current launch only - which is
the right meaning for a gate.

`relaunch-file-readback` is the worked scenario: launch 1 starts on
Foreign, `cmd+shift+right` cycles to Themed (which posts `atrium_core_save()`),
the file must then hold Themed's id, and launch 2 must come up on Themed's tab
with no key pressed.

### Measuring movement rather than colour

```json
{"type": "pixels_changed", "before": "before", "after": "pulled",
 "region": [10, 240, 200, 40], "min_changed_pct": 40.0}
```

`theme_changed` grades `pixcmp diff`, whose delta is a euclidean distance
between the two region **means**. Averaging the region before comparing it has
now been caught reading near zero for working behaviour twice:

- **Cancellation.** A region spanning both ends of a movement scores near zero,
  because what leaves one end and arrives at the other cancels in the shared
  average. On `sidebar-vertical-band`'s own frames the region `[10,120,200,200]`
  reads a mean delta of **0.03** while **32.34%** of its 40,000 pixels changed.
- **Desaturation.** The delta also carries the magnitude of the colour change,
  so it falls when a thing still moves but is painted paler.
  `sidebar-vertical-band` read **9.88** against a bar of 10.0 for weeks while its
  gesture worked perfectly - the row pill had lost its tint, not its motion.

`pixels_changed` compares corresponding pixels and counts how many moved further
than `tol` (default 12, a euclidean RGB distance). Nothing is averaged before the
comparison, so nothing cancels, and the count is scale-free. Across the tint
regression that moved the mean delta 45 -> 9.88 -> 125, this reading went
74.42% -> 73.38% -> 74.06%.

The two are companions, not alternatives: `pixels_changed` says the content
moved, `theme_changed` says the colour is right. Running one alone is how both
misses happened.

**Derive the threshold from stored frames and write down the numbers.** The bar
lives in the assertion's `desc`, with the readings it came from - a threshold
tuned against 45 sat quietly missing at 9.9 for weeks because nobody could see
what it had been derived from. `python3 build/scenarios/lib/moved_outcome_test.py`
(`make moved-outcome-test`) pins both halves of the gap the bar sits in.

## Settings window (settings-window milestone)

`Cmd+,` and the app menu's "Settings..." item are `IDC_OPTIONS`. When the
dylib exports `AtriumOpenSettings` (resolved standalone via dlsym, same
posture as `AtriumToggleSidebar` - no ABI group gate), the C++ intercept in
`AtriumNativeWidgetMac`/`AtriumBrowserWindow::ExecuteCommand` claims BOTH the
key-equivalent AND the menu-item dispatch paths and routes to Atrium's own
Swift-owned settings window instead of `chrome://settings`. Without the
export, `IDC_OPTIONS` falls through untouched and both paths open native
`chrome://settings` - `chrome://settings` stays reachable by URL either way,
Atrium settings is additive, not a replacement.

The settings window is a process-singleton `NSWindow` (not a per-browser-window
child widget like the command bar) - one instance regardless of how many
browser windows exist, and it survives any/every browser window closing.
Escape and the red close button both hide it (not deallocate); reopening
restores the same hosting view, but every open resets the selected pane to
General (`SettingsModel.reset()`, by design). Frame persists via
`NSWindow.setFrameAutosaveName("AtriumSettings")`; open/closed state itself
does not persist across relaunch (non-goal, v1).

### Degradation matrix

| Condition | Effect |
|---|---|
| Degraded dylib (no `AtriumOpenSettings` export) | `Cmd+,` / Settings menu item open native `chrome://settings`; no crash |
| Stale C++ build (no `set_downloads_directory`/`set_prompt_for_download` ops) | General pane's downloads controls hide (Swift nil-checks each op field, the `set_sidebar_width` convention); everything else in the settings window works fully |
| Command-bar ABI group never connected | General pane's default-search-engine section hides entirely |

Menu routing: upstream `main_menu_builder.mm` gives the "Settings..." item an
explicit `.target(app_delegate).action(@selector(showPreferences:))`, which
bypasses the CommandDispatcher intercept for both the menu click and the
`Cmd+,` key equivalent - `atrium_settings_menu_hook.{h,mm}` retargets that
item once at startup to an Atrium handler that opens Atrium settings when
`can_open_settings()` and forwards to the stored stock target/action
(native `chrome://settings`) otherwise.

### `settings.json`

Lives next to `spaces.json`/`hotkeys.json` (env seam `ATRIUM_SETTINGS_FILE`),
`schemaVersion` 1, atomic writes, missing file -> defaults written once,
newer schema -> pure defaults with the file left untouched, each enum field
decodes leniently (unrecognized value falls back to its own default without
discarding the rest of the file):

```json
{ "schemaVersion": 1,
  "appIconVariant": "crimson-ink",
  "animationsEnabled": true,
  "startupBehavior": "restoreLastActive",
  "downloadsDirectory": null,
  "promptForDownload": false,
  "sidebarPosition": "left" }
```

`downloadsDirectory`/`promptForDownload` are Swift-side display mirrors only -
the authoritative state is the profile pref the `set_downloads_directory`/
`set_prompt_for_download` ABI ops set. Deliberately NOT here: hotkeys
(`hotkeys.json` is the backing store), sidebar width (`spaces.json`'s
`AppState.sidebarWidth`), search engine (profile prefs, C++-side).

### App icon pipeline

The 22 source SVGs under `build/icons-src/` (the default `crimson-paper`, the
`auto` pair, the dark `crimson-ink` variant, and an `-accent` composition per theme, all 19 themes) are generated by
`build/scripts/gen-brand-icons.py` from the Brand Book v3 murmuration mark
(`docs/brand/brand-book.html`'s `flow()`/`renderVals()`) - re-run it after
changing a theme or the mark geometry rather than hand-editing the SVGs.
The tile is the brand book's `iconTile`: a fixed base (`PAPER_BASE` white,
`INK_BASE` dark gray, or the theme accent), a vertical falloff, and the
ambilight corner wash at `WASH_DARK` (0.2) or `WASH_LIGHT` (0.2). Change
these values in both files together.
The other 18 themes have no `-ink` variants, because user feedback said
they all read as near-identical dark tiles.

The generator writes a second output per variant: an Icon Composer package at
`build/icons-src/<slug>.icon/`, plus the default `crimson-paper` stack under
the bundle name `AppIcon.icon`. It splits the flat tile across the system
compositor - the base and its falloff become the `icon.json` `fill` gradient,
the corner wash a plain layer, and the flock a plain layer on top (a glass mark
washed out). Only `crimson-paper` and `AppIcon` set group translucency (1.0),
Arc-style. `auto.icon` is the one two-appearance stack: the `crimson-paper`
layers for light and the `crimson-ink` layers for dark, keyed by
`hidden-specializations`. Xcode 26.6's `actool` drops every
`*-specializations` array, so the compiled `auto` stack shows the light
artwork alone until a later toolchain honours the key.
`color-space-for-untagged-svg-colors` must stay `display-p3`: every other value
crashes `actool` instead of reporting a validation error.

`make icons` (`./build/scripts/build-icons.sh`) regenerates the 22 app-icon-variant
PNGs from `build/icons-src/*.svg` via `qlmanage`, then pipes each
through `build/scripts/mask-icon-alpha.py` (`qlmanage -t` composites onto opaque
white, so corners need a rounded-rect alpha mask punched back in), committing
the output under `build/icons/`. Re-run after editing a source SVG. The settings
window's Appearance pane picker only reads the committed PNGs, not the SVGs.

### Bundle icon (Assets.car and .icns)

`make icns` (`./build/scripts/build-assets-car.sh`) runs one `xcrun actool` over
every `build/icons-src/*.icon` and writes two committed binaries under `build/`,
deliberately not under `$SRC/patches/`, so the patch series stays text-only:

- `build/Assets.car`: 23 `IconImageStack` entries, each named after its `.icon`
  directory, so the runtime reaches a variant with `[NSImage imageNamed:@"<slug>"]`.
- `build/atrium.icns`: the legacy icns `actool` emits for the `--app-icon` stack.

One invocation compiles the whole set - `actool` overwrites `Assets.car` rather
than merging into it, so a per-variant loop would keep only the last variant.
`build/scripts/build-icns.sh` is the superseded flat-PNG path and is no longer
wired to a target.

`build/scripts/inject-icns.sh` copies both into the built bundle
(`$SRC/out/atrium/Atrium.app/Contents/Resources/`), overwriting Chromium's own
`Assets.car`, and sets `CFBundleIconName=AppIcon` in the built `Info.plist`
before re-signing ad-hoc (`codesign --force --sign -`). That key is what points
the Dock, Cmd+Tab, Force Quit and Finder at our stack - only a stack renders as
real Liquid Glass, so it must stay. The script runs at the end of
`build/scripts/build-shell.sh` (i.e. after `make build`), no-ops when an input
or the app bundle is missing, and is idempotent - a second run skips the
copy+resign when the bundle already matches.

It also ships the 21 variant PNGs into
`Contents/Resources/atrium-icons/`. The Appearance pane's picker and the
runtime Dock swap both read them from there, so the `.icns` alone is not
enough. The copy is idempotent the same way: a PNG travels only when it
differs, and one whose source is gone is deleted from the bundle.

This sets the icon every bundle-level surface resolves to. The DOCK alone
follows `appIconVariant` at runtime: `AtriumApplyAppIcon`
(`atrium_app_icon_mac.mm`) sets `NSApp.applicationIconImage` from the staged
PNG, at launch and again on every settings save. Finder, Cmd+Tab, Force Quit
and About keep showing `app.icns` until the next `make icns` and relaunch.

## Peek mode (peek-mode milestone)

Shift+click on a link now opens a floating preview card instead of a new
window - the peek widget shows the target page without navigating the
current tab or opening a real tab/window. **This is a semantic change**:
native "open in new window" via shift+click is GONE, replaced by peek.
Right-click "Open Link in New Window" is unaffected - the intercept filters
on `!started_from_context_menu`, so an explicit context-menu new-window
request still opens a real window either way.

Interception point: `Browser::OpenURLFromTab`, filtered on
`disposition == NEW_WINDOW && is_renderer_initiated &&
!started_from_context_menu` (Mac only; `window.open`/`target=_blank` never
reach this path - they route through `AddNewContents`, untouched). Fourth
optional ABI group, `peek_connected_`, resolved the same AND-gated dlsym
pattern as spaces/command-bar - CORE/spaces/command-bar are unaffected if it
fails to resolve.

- Ops (appended to `AtriumHostOps`): `peek_promote(host)`, `peek_dismiss(host)`.
- Exports: `AtriumCreatePeekChrome(host, ops, slotID) -> NSView*` (+1
  retained - Swift chrome strip only: title/URL/close/promote, not the
  previewed page itself, which is native), `AtriumOnPeekOpened(host, url)`,
  `AtriumOnPeekMetaChanged(host, title, url)`, `AtriumOnPeekClosed(host)`.

### Degradation matrix

| Condition | Effect |
|---|---|
| Degraded dylib (no `peek_connected_` group) | shift+click falls back to stock NEW_WINDOW behavior - a real new window opens, no crash |
| Dylib with peek group | shift+click opens the peek widget; current tab's URL unchanged |

### Promote / dismiss

- **Promote** (chrome strip button): the peek's live `WebContents` is
  inserted into the tab strip adjacent to the source tab via
  `InsertWebContentsAt`, ACTIVE, no reload - the same `WebContents` object
  continues rendering. The widget closes instantly, no dismiss animation.
- **Dismiss** (Escape, chrome strip close button, click-out): all three
  funnel through one `ClosePeek` path, which destroys the peek
  `WebContents` - no persistence, no "recently peeked" list. Escape reaches
  `ClosePeek` via the `WebContentsDelegate` unhandled-key route: the peek
  WebContents' delegate is the `PeekWidget` itself, so an Escape keystroke
  the page doesn't consume bubbles straight to the widget.
- **Geometry**: the card fills nearly the
  entire web-content pane - sized against `AtriumBrowserWindow::
  GetWebContentBoundsInScreen()` (the pane to the right of the sidebar),
  inset by a 16px margin on all sides, ~14px rounded corners (`masksToBounds`
  on the widget's window content layer, clipping the chrome strip and
  WebView identically), and a real `NSWindow` drop shadow (`hasShadow`,
  shape follows the rounded content automatically). Supersedes the original
  plan's ~640x480/80%-of-parent proposal.
- Open/dismiss are CA animations (scale + opacity, ~240ms open ease-out,
  ~170ms dismiss ease-in), anchored at the screen point the triggering
  shift+click landed on (`display::Screen::GetCursorScreenPoint()`, captured
  in `atrium_peek_intercept.mm` and threaded through `OpenPeek`) rather than
  the card's center - open zooms in FROM that point, dismiss zooms back
  TOWARD it. Falls back to a center anchor if no origin is available. A
  loading placeholder (clipped to the same rounded corners) is shown until
  the peek's first visually-non-empty paint.

**Same-profile peek (deliberate):** the peek's `WebContents` is created in
the SAME profile as the source tab, not OTR/incognito. This is what makes
the no-reload promote flow work (the destination tab strip is the same
profile's) - but it also means a peeked page's history/cookies are
identical to a real visit. This is a considered design decision, not a
silent default; see the plan's Non-Goals for the OTR alternative.

### Known limitations

| Limitation | Detail |
|---|---|
| `window.open`/`target=_blank` inside a peek | Silently no-ops (default delegate) - consistent with the no-peek-of-peek non-goal, not a bug |
| Animations bypass settings | The C++ CA animations don't honor Swift's `animationsEnabled` setting (no ABI channel yet) or reduce-motion - same posture as the sidebar overlay |
| In-preview navigation | Following a link inside the preview loads in place with no back/forward UI - peek is a single-URL preview, not a mini-browser (plan non-goal) |

### Auto-peek trigger

A plain (unmodified) click on a link inside a PINNED or FAVORITED tab now
auto-peeks when the target is CROSS-SITE (different eTLD+1) - Arc parity. A
same-site link navigates the pinned tab in place, keeping pinned web-apps
(Gmail/Notion) usable. Shift+click (above) stays as the power-user bonus path
from any tab.

Intercept is a `content::NavigationThrottle`
(`atrium_peek_navigation_throttle`), NOT the shift+click `OpenURLFromTab` hook:
a plain link click never emits the `OpenURL` IPC (it resolves renderer-side via
Blink's `BeginNavigation`), so it never reaches `OpenURLFromTab` OR
`chrome::Navigate` - the same structural fact the traffic-routing section's
"plain same-tab clicks never route" limitation records. At `WillStartRequest`
the throttle checks primary-main-frame + renderer-initiated + user-gesture +
`PAGE_TRANSITION_LINK` + http(s) + cross-site + pinned/favorited eligibility;
on a match it posts a task to open the peek and returns `CANCEL_AND_IGNORE`
(silent cancel, no error page, pinned tab unchanged). Every miss is `PROCEED`.

Eligibility ("is the source tab pinned/favorited") is a fifth peek export,
`AtriumIsPeekSourceTab(host, tabId) -> bool`, resolved SEPARATELY from
`peek_connected()`'s four-symbol gate. The two peek paths' capability checks
are independent: shift+click needs only the original four exports; the auto
path additionally needs this one.

#### Degradation matrix (auto-peek)

| Condition | Effect |
|---|---|
| Older dylib: four peek symbols but no `AtriumIsPeekSourceTab` | Shift+click peek fully works; auto path inert - the throttle is never even registered (`MaybeCreateAndAdd` gates on the fifth symbol), zero per-navigation cost, no crash |
| Degraded/vanilla dylib (no peek group) | Neither path; stock behavior |

#### Known limitations (auto-peek)

| Limitation | Detail |
|---|---|
| Cross-site download link | A cross-site link that turns out to be a download peeks first, then the download proceeds from the peek's WebContents - `WillStartRequest` cannot know it is a download yet (accepted v1 edge) |

### Folded pinned-tab features (Arc M2)

| Feature | Behavior |
|---|---|
| Reset Tab | Context-menu item on a pinned row navigates it back to its pin-time URL (`SpaceTab.pinnedURL`, captured at pin, cleared on unpin/cross-space demote); a cold row resets its stored URL for next materialization |
| Collapse pinned section | A sidebar-header chevron hides the pinned rows (favorites strip + regular tabs unaffected); per-space `Space.pinnedCollapsed`, persisted across relaunch |
| Folder hover-peek | Hovering a collapsed folder row shows a SwiftUI popover listing its member tabs (favicon + title); clicking a member activates it - not a web-content peek |

## Traffic routing (traffic-routing milestone)

Hand-edited rules steer navigations to a target space (and, if needed, the
profile/window that owns it) instead of opening where the click/type
happened. Matching is entirely Swift-owned; C++ only asks "where should this
land?" via one synchronous export and acts on the answer.

| Trigger | Seam | Behavior |
|---|---|---|
| Typed URL (pill), command-bar accept | Swift seam, before the op fires | `routeTypedNavigation`/`newTabWithURL` consult the coordinator BEFORE `ops.navigate`/`newTabWithURL` - routed opens on the target host directly, no C++ hook involved |
| Cmd/middle-click new-tab, right-click "Open Link in New Tab" | Hook 1: `chrome::Navigate()` | Same-profile: passthrough, Swift's pre-arm finishes the job. Cross-profile: cancelled, reopened on the target controller |
| Link click, same tab (`CURRENT_TAB`) | Hook 1 | Cancelled + reopened in the target space; origin tab closed only if fresh (`IsInitialNavigation()`) |
| Plain `target=_blank` click (no modifier), `window.open()` | Hook 2: `Browser::AddNewContents` | The renderer pre-creates `new_contents` for both before `chrome::Navigate()` ever runs, so Hook 1 never sees either (see the peek section's identical statement above). Same-profile: contents kept, Swift's stamp confirms on commit. Cross-profile: `new_contents` discarded, reopened on the target controller |

Fifth optional ABI group, `routing_connected_` - a single-symbol AND-gate
(the `command_bar_connected_`/`peek_connected_` dlsym pattern), because the
hooks must never fire against a dylib that cannot match. Group status log
line: `... routing=<0|1>`, appended after `peek=`.

- Export: `AtriumCopyRouteForURL(host, url) -> char*` - synchronous,
  main-thread. Returns a malloc'd `{"spaceID": "<uuid>", "profileID":
  "<profile basename>"}` on a match, `NULL` otherwise. Caller (C++) owns the
  buffer and must `free()` it - the `AtriumCopyRequiredProfilesJSON`
  ownership contract. No new `AtriumHostOps` fields.
- One deliberate side effect: a matching call arms the cold-adoption queue
  and a routing ledger record for that route before returning, so whichever
  path actually inserts the tab (Hook 1 passthrough, C++ reopen, Hook 2
  keep, Swift seam reopen) is finished by the existing adopt/confirm
  pipeline - C++ never makes a second call to report what it did.

### `routing.json`

Lives next to `spaces.json`/`hotkeys.json` (env seam `ATRIUM_ROUTING_FILE`),
loaded once at wiring time (no watcher - relaunch applies edits),
`schemaVersion` 2, per-entry lenient decode (one malformed rule dropped and
logged, siblings still load), unparseable file or newer schema -> empty
rules, file left untouched (never-clobber-newer), missing file -> empty
defaults written once:

```json
{ "schemaVersion": 2,
  "defaultTargetSpaceID": "",
  "rules": [ { "id": "<uuid>", "enabled": true,
               "matchType": "contains", "pattern": "corp.example",
               "targetSpaceID": "<space uuid>",
               "excludedSourceSpaceIDs": [] } ] }
```

| `matchType` | Tests against | Notes |
|---|---|---|
| `contains` | URL's host only, case-insensitive substring | Literal match - a leading `*.` is NOT a wildcard, it's matched literally (pinned by a regression test) |
| `regex` | Full URL string (host + path + query), case-insensitive `NSRegularExpression`, pre-compiled at load | Covers path/query-based rules `contains` cannot express; invalid pattern = that entry dropped |

| Field | Meaning |
|---|---|
| `defaultTargetSpaceID` | Space for a URL no rule claims. Empty string means off. |
| `targetSpaceID: "current"` | The tab stays where the navigation started. Ends the search. |
| `excludedSourceSpaceIDs` | The rule is skipped when the navigation starts in one of these spaces. |

Array order = priority, first enabled match wins. `targetSpaceID` resolves
its owning profile via `SpacesStore.shared.spaces` at match time - no
denormalized profile field. The Routing pane in Settings edits every field.

### Unrouted by construction

`atrium::ScopedRoutingBypass` (a file-static bool + `base::AutoReset` RAII)
wraps `BrowserController::NewTabWithURL`'s `chrome::AddTabAt` call itself, so
every Swift-initiated open - cold adoption, favorites, startup restore, the
routing seam's own target-host open, undo's reopen - is Swift-initiated, not
navigation-initiated, and therefore never re-enters the hooks. This is what
makes routing loop-proof without cycle detection. The first-bootstrap
startup tab (`atrium_browser_controller.mm` window-bootstrap `AddTabAt`) is
now wrapped too, defensively - it was previously safe only because it runs
before that host's routing wires attach, not because of the bypass pattern
every other `AddTabAt` use site relies on.

### Toast and undo

Every route (typed, link, `window.open`, same- or cross-profile) shows one
toast shape for 4s (`AtriumMotion.animation(_:)`-driven, nil under
reduce-motion/animations-disabled). Undo replays the move: same-profile
reuses the `moveTabToSpace`/`moveLiveTab` path; cross-profile reopens on the
origin host, closes the routed tab, and raises the origin window - armed via
the same coordinator arm-pattern with `isUndo: true` so the undo's own
confirm never re-toasts or re-swaps.

A routed cross-profile confirm always calls `switchToSpace` (the M2b
hidden-window swap) regardless of disposition - a background Cmd-click
cross-profile route swaps the window into view too, not just foreground
navigations. One behavior for all dispositions in v1.

### Degradation matrix

| Condition | Effect |
|---|---|
| Degraded dylib (no `routing_connected_` group) | `routing=0`; hooks short-circuit; zero behavior change; no crash |
| Stale chrome build (no hooks) + current dylib | Typed-URL/command-bar routing still works - `registerHost` wires the coordinator itself at host registration, independent of any C++ hook call. Link-click and `window.open`/`target=_blank` triggers are inert: Hook 1/Hook 2 never fire without the chrome-side hooks, so there's nothing to intercept those navigations |
| Missing/malformed/newer-schema `routing.json` | Empty rules; file never clobbered |

### Known limitations

| Limitation | Detail |
|---|---|
| Plain same-tab link clicks never route | Renderer-internal navigation resolves via Blink's `BeginNavigation` without ever reaching `chrome::Navigate()` - structurally invisible to Hook 1. Cmd/middle-click, right-click "Open in New Tab", and typed URLs are unaffected. A `NavigationThrottle` same-tab safety net is the spec-sanctioned follow-up, not built in this milestone |
| `window.open()` during HTML5 content-fullscreen bypasses Hook 2 | Upstream `Browser::AddNewContents` defers popup creation and returns before Hook 2 runs when the opener is in content (not browser) fullscreen (`chrome/browser/ui/browser.cc`, the `FullscreenTabOpeningPopup`/`RunOrDeferUntilTransitionIsComplete` path) - routing is silently inert for that one call; narrow, not probed by Task 7 |
| No hot-reload | `routing.json` loads once at wiring; edits need a relaunch, same posture as `spaces.json`/`hotkeys.json` |
| Cross-profile routes need the target profile loaded this session | A target space whose profile has no registered host this session falls through natively (the settings-workspaces-pane relaunch caveat) |
| Redirect-confirm residual | A server redirect that rewrites the URL before the first `OnTabURLChanged` relay can defeat the exact-match confirm - same accepted class as `ColdTabAdoptionQueue`'s existing FIFO residual |
| http(s) only | `chrome://`, `file://`, and other non-http(s) schemes are never routed. Guarded once, Swift-side, at the top of `RoutingCoordinator.decideRoute` - the one chokepoint both the C++ hooks' `AtriumCopyRouteForURL` call and the Swift typed-URL/command-bar seam's `routeTypedNavigation` go through, so the guard covers both (the C++ hooks also carry their own `SchemeIsHTTPOrHTTPS` check, belt and braces) |
| Regex cost on the navigation path | `regex` rules run `NSRegularExpression` (ICU) against the full URL of every routable navigation. A pathological user-authored pattern can backtrack catastrophically, stalling navigation - acceptable for a personal hand-edited file, but note the URL side is attacker-influenceable (long query strings), so keep patterns anchored and simple |

## Theme Studio (theme-studio + theme-per-space milestones)

Per-space gradient backdrops (`set_backdrop_theme` op -> `AtriumBrowserWindow::
SetBackdropTheme`: bitmap crossfade + native grain). The theme designer is the
**sole per-workspace appearance editor** - open it by long-press (~0.4s) or
right-click "Edit Theme…" on a sidebar space card. Each workspace stores one
`ThemeSpec` in `themes.json`; night shift and ambient are per-workspace fields on
that spec.

### Model (theme-per-space)

| Concept | Behavior |
|---------|----------|
| Solid = 1-stop | A theme with ONE color stop renders as a flat solid backdrop (the old tint look). Add a second stop -> gradient. No separate solid mode. |
| Night shift / ambient | Per-workspace `ThemeSpec.nightShiftEnabled` / `ambientEnabled` (designer toggles). Moved OUT of global settings. Only spaces that opt in warm/animate. |
| Night-shift warmth | Baked per-space at backdrop push: `ThemeRuntime.warmthOffset(for:)` = clock curve `0.44*(1+cos(2π(h-2)/24))/2` when the space opts in, else 0. Peak at 02:00, zero at 14:00. `wf = warmth*0.12` nudges stop R up / B down in `ThemeMath.rasterize`. |
| Ambient timer | 12 Hz timer runs only while some active space's theme has `ambientEnabled`; `ThemeAnimator.refresh()` starts/stops it on space switch / theme commit / animations-enabled change. Reduce Motion gates it off. |
| `Space.tint` | Now a DERIVED cache = dominant color of the workspace's `ThemeSpec` (`ThemeMath.dominantTintHex`), recomputed on commit/preview. Still the liquid-glass palette source (`TintPalette`, 4.582:1 floor at L=0.1791), so glass contrast is unchanged. 1-stop -> tint = that stop's color, darkened toward black (hue preserved) when it doesn't already clear the L=0.1791 ceiling. |
| Lazy migration | A theme-less space (tint, no `themes.json` entry) renders its flat tint unchanged; opening it in the designer synthesizes a 1-stop theme from the tint (`effectiveTheme`). Lazy: nothing is written to `themes.json` until the user commits an edit. New spaces get a stored 1-stop theme at creation. |
| Retired settings keys | `settings.json` no longer carries `nightShiftEnabled` / `ambientEnabled`. Schema stays 1; an old file still carrying them decodes clean (JSONDecoder ignores unknown keys). No color picker anywhere (space card, Settings > Workspaces rows, Create-Space form). |

ABI unchanged: `set_backdrop_theme` still takes one per-host rasterized RGBA8
bitmap + grain + transition-ms; warmth/ambient are resolved Swift-side before the
push, so no C++/Chromium rebuild is needed for this milestone.

### Known limitations

| Limitation | Detail |
|---|---|
| Night-shift feel | Warmth magnitude was VM-measured (identical-color A/B, ~4% channel shift at offset 0.33), but the "looks right at a real evening" judgment is owed to the user's eyes on hardware. |
| Ambient drift feel | VM confirmed the positive direction (opted-in space animates, opted-out static); smoothness over time and the trackpad stop-drag feel in the designer need a hardware pass. |
| Ambient stop edge | The "timer stops when the last opted-in space toggles off" path is unit-tested (`ThemeAnimatorTests`), not separately VM-probed. |

### `themes.json`

Lives next to `spaces.json` (env seam `ATRIUM_THEMES_FILE`), `schemaVersion` 1,
keyed by space UUID, per-entry lenient decode, missing file -> no theme (flat
tint, no file written). To seed a VM probe: write the file, point
`ATRIUM_THEMES_FILE` at it, and give the active space in `spaces.json` a
matching UUID key:

```json
{ "schemaVersion": 1,
  "themes": { "<space-uuid>": { "name": "…",
    "stops": [ { "x": 0.2, "y": 0.25, "color": "#275D68", "alpha": 1.0 } ],
    "opacity": 1.0,
    "effects": { "grain": 0.35, "vignette": 0.22, "frost": 0, "warmth": 0 },
    "darkAdaptation": 0.45, "version": 1,
    "nightShiftEnabled": false, "ambientEnabled": false } } }
```

`nightShiftEnabled` / `ambientEnabled` are captured through native decode,
`decodeLenient`, sanitize, and round-trip (an old file without them decodes to
`false`). `ThemeStore` rewrites this file on any edit (upper-casing the UUID key
per `UUID.uuidString`; read is case-insensitive) - reseed a staged copy before any
run that asserts file content. Fixtures: theme-studio round
`build/vm-fixtures/fixture-theme*.json`; theme-per-space round
`build/vm-fixtures/fixture-tps-*.json`.

## Split view (split-view milestone)

Two tabs of one space shown side by side (or stacked) in the content area, with
a draggable divider. The pair is Swift-owned over an untouched TabStripModel -
C++ only renders the panes and echoes authoritative state; Swift owns intent,
arrangement, and persistence.

### Pane model

- Exactly two panes, `primary` (start) and `secondary` (end), in ONE window (=
  one (slot, profile) Browser). Orientation `sideBySide` (divider vertical) or
  `stacked` (divider horizontal); default `sideBySide`, ratio 0.5.
- Each pane = one live tab of the SAME space. Cold rows materialize first.
- Active pane = the strip's active tab. Everything that means "the tab" (URL
  pill, nav band, Cmd+W, command-bar targets, modal anchoring) tracks the active
  pane; the secondary pane's tab is visible but not strip-active.
- Activating a third tab while split REPLACES the active pane's tab; the split
  survives (Arc behavior, falls out of `ShowTab` routing). Clicking into a
  pane's web content activates it (focus-driven, highlight flip only).

### Entry

Sidebar tab-row right-click -> "Open in Split View", offered on a non-active row
when no split is active. Live row splits immediately (row's tab = secondary,
current active = primary). Cold/favorite row materializes first
(`new_tab_with_url` + `ColdTabAdoptionQueue`), then splits the new tab as
secondary against the prior active as primary. While split, both member rows'
menus gain a "Split View" submenu: Side by Side / Stacked (checkmark = current)
+ Break into Separate Tabs.

A sidebar row dragged onto the left, right, top or bottom quarter of another
live row splits too (`sidebarTabSplit`: dragged tab, target tab, side). The
handler activates the target row, then inserts the dragged page at that edge
through the same `InsertPaneFromDrop` the content-area drop uses. Left and right
give a vertical divider, top and bottom a horizontal one. The middle band of a
row keeps the reorder drop line. Cold rows and folder heads carry no tab id and
never split.

The handler refuses the drop when the window is already split, when either tab
is outside the active space, or when the pane declines to show the target. Every
entry reports the new split through `AtriumOnSplitChanged`, the drop included,
so the sidebar hides the edge quarters while one is up.

### ABI

Sixth optional ABI group, `split_view_connected_` - the single AND-gated dlsym
pattern (`routing_connected_`). Group status log line: `... split_view=<0|1>`,
appended after `routing=`. CORE and the other groups are unaffected if it fails
to resolve.

- Ops (appended to `AtriumHostOps` after `set_backdrop_theme`):
  `set_split(host, secondary_tab_id, orientation, ratio)` - enter; the host's
  current active tab = primary. `update_split(host, orientation, ratio)` -
  convert orientation / apply ratio. `close_split(host, keep_tab_id)` -
  dissolve; `keep_tab_id` 0 = keep the active pane's tab. C++ validates both
  tabs live in the host's strip (unknown/foreign = logged no-op) and clamps ratio.
- Export: `AtriumOnSplitChanged(host, json)` - the authoritative C++ -> Swift
  echo, one export with a `reason` field, fired on every state change:
  `{"active":bool,"primaryTabID":n,"secondaryTabID":n,"orientation":"sideBySide"
  |"stacked","ratio":double,"reason":"op"|"tab_closed"|"moved_out"|"divider"}`.
  An `active:false` echo's `orientation`/`ratio` are always the defaults, not the
  last split's values. Divider drag echoes once, drag-end only. Swift reconciles
  its `SplitState` and persistence from the echo, never from its own optimistic
  write (the sidebar-width authority contract).

### Layout, divider, clamps

The two cards split the content rect with a 10pt tinted-glass gutter between
them - the resize area, reusing the sidebar grab-line hover treatment. Min pane
extent 200pt with upstream's 10%-of-available clamp for narrow windows; ratio
snaps to 0.5 within a 15pt window. Geometry copied from upstream
`multi_contents_view` (pattern-reusable, not link-reusable - it is BrowserView-
coupled). Single-pane mode lays out pixel-identically to pre-split; hit-testing
returns both cards and the divider as client area, never a window-drag region.

### Dissolution rules

| Trigger | Effect | Persisted record |
|---|---|---|
| Break into Separate Tabs | dissolve, active pane's tab shown full-card; both tabs stay live | cleared |
| Cmd+W / row close / page self-close / crash | collapse to the survivor, deterministically strip-activated | cleared |
| Cross-window move-out of a split tab | collapse to survivor, NO freeze snapshot (a split window still has live content) | cleared |
| Cross-space switch | dissolve (visual only) | KEPT (auto re-split on return is a later milestone) |

Conservation invariant (from tab-org): split mutations never delete a
`SpaceTab`. Collapse runs synchronously BEFORE the freeze/suppress guards, which
therefore only ever see single-pane semantics.

### Persistence + restore

`Space.split: SplitArrangement?` (additive, `schemaVersion` stays 1, the
`Space.groups` `decodeIfPresent` recipe): `primaryURL`/`secondaryURL` (`SpaceTab`
is id-less, so URL-keyed), `orientation`, `ratio`. Written through from the
authoritative echo on create / convert / divider-commit; cleared per the table
above. A pre-split `spaces.json` decodes clean.

**Launch restore is ON** (`defaultSplitLaunchRestoreEnabled = true`). A
persisted split + relaunch re-materializes the partner tab and re-enters the
split. The bootstrap reentrancy hazard that previously blocked this - a
TabStripModel reentrancy CHECK (`tab_strip_model.cc:140 !*guard_flag`) from the
partner adoption re-entering the strip during bootstrap - is fixed by
deferring both the partner materialization and the `enterSplit` call via
`runLater`, the same fix already used by `enterSplitFromColdRow`.

### Degradation matrix

| Condition | Effect |
|---|---|
| Degraded dylib (no `split_view_connected_` group) | `split_view=0`; no split ops attempted; no menu items; pre-split single-pane behavior; no crash |
| Vanilla / no dylib | as above |
| Missing/malformed/newer-schema `spaces.json` split field | decoded as no split; file never clobbered |

### Split-command crash guards (A1/A2)

Atrium builds no BrowserView, so stock split-tab entry points NOTREACH on
Atrium's tab model. Guarded additively:

| Stock entry | Guard |
|---|---|
| "Open Link in Split View" link context-menu item | Hidden on Atrium windows (`IsAtriumBrowserWindowEnabled()` gate in `render_view_context_menu.cc`) |
| Cmd+Option+N (`IDC_NEW_SPLIT_TAB`) | Swallowed in `AtriumNativeWidgetMac::ExecuteCommand` |
| chrome://bookmarks "Open in split view", bookmark-bar, tab-strip "Add to New Split" | Structurally unreachable (no BookmarkBarView / TabMenuModel); VM-probed no crash |

### Non-goals (v1)

More than two panes / nested splits; cross-space or cross-profile panes;
drag-to-content-edge or command-bar entry; pane drag-to-reorder / swap;
TabStripModel split-tab (`AddToNewSplit`) adoption; session-service integration;
split UI in the hover-overlay sidebar beyond the inherited row affordance;
keyboard-driven divider resize. DevTools
docking is Phase C, a separate later milestone reusing this pane framework.

### Known limitations

| Limitation | Detail |
|---|---|
| Launch restore is slot-0 only | Only the first (slot-0) window's split restores - other windows are not restored at all yet |
| Cold-row split needs a tracked prior active tab | The materialized cold tab lands as secondary against the prior *tracked* active tab. If the active tab is an untracked ephemeral new tab (no `spaceID` - e.g. a fresh startup/Cmd+N blank NTP), no prior is known and the split does not enter (rather than a degenerate self-split). Entry from any live/persisted active tab is unaffected |

## Load indicator (todo batch 40-53)

A two phase load indicator in the chrome. No mainstream browser draws a bar
over the page, and Chromium reports no progress before the first byte, so
the wait is its own phase rather than a fake 6 percent.

A nested `LoadProgressObserver` (`content::WebContentsObserver`) watches the
window's ACTIVE tab only. `RetargetLoadProgress()` re-points it on every
seam where the active tab or active pane changes (all `ShowTab` returns,
`EnterSplit`, `FinishCloseSplit`) and ends the run first - this funnel is
also what the status bubble's force-hide rides on.

Its three callbacks push one script into the sidebar document and the devbar
document:

```
window.atriumLoadPhase && atriumLoadPhase(tabId, phase, fraction)
```

| Phase | Pushed on | Fraction |
|---|---|---|
| `waiting` | `DidStartLoading` | 0 |
| `receiving` | `LoadProgressChanged` | the monotonic max so far |
| `done` | `DidStopLoading` | 1 |

The fraction is monotonic for the run, so Chromium's reset-to-low on a
mid-load navigation cannot snap the fill backward. `atriumTabLoading` still
owns whether a ring shows at all, and the phase push says how far round it
has travelled.

Three surfaces read the push. `load-fill.js` builds the fill layer the
docked address field and the floating capsule both use, and `loading-mark.js`
puts the row and tile rings into their second phase. Every easing is a CSS
transition, so no browser-side timer runs.

Split view v1: active pane only - the observer tracks one WebContents.

### Known limitations

| Limitation | Detail |
|---|---|
| A background tab loses its fill on a tab switch | The field shows the active tab only, so `RetargetLoadProgress` pushes `done` for the tab it leaves. That tab's ring keeps running on `atriumTabLoading`, but its comet no longer fills |

## Link-hover status bubble (todo batch 40-53)

Hovering a link shows a themed, rounded bubble at the bottom-left of the
active pane's content card with the elided target URL
(`url_formatter::ElideUrl`, the same helper stock Chrome uses). Pure
C++/views, same child-widget primitive and degradation posture as the
command bar - no dylib dependency.

**Why `GetStatusBubbles()` stays stubbed** (the load-bearing fact): upstream
`Browser::UpdateTargetURL` `static_cast`s every returned `StatusBubble*` to
`StatusBubbleViews` and its `base_view()` to `ContentsWebView`, unchecked -
Chromium has never had a second production `StatusBubble` implementation.
Atrium's content view is a plain `views::WebView`, not a `ContentsWebView`,
so returning any Atrium-owned object from `GetStatusBubbles()` would make
those casts invalid the moment a link is hovered (`ContentsMouseEvent` does
the identical pair). `AtriumBrowserWindow::GetStatusBubbles()` therefore
still returns `{}`; instead `atrium_status_bubble_hook.{h,mm}` adds one
`BUILDFLAG(IS_MAC)` line at the top of `Browser::UpdateTargetURL` that
resolves the Atrium controller (the same is-this-Atrium gate peek uses) and
forwards to `AtriumBrowserWindow::SetStatusBubbleURL`.

Behavior: a 75ms show delay debounces a quick mouse pass over a link;
retargeting link-to-link while visible updates instantly with no
re-debounce; mouse-out fades over 150ms. Tab/space/split switches force-hide
instantly via `RetargetLoadProgress`'s funnel (zero extra call sites), and
teardown resets the widget alongside the progress widget. Only the active
pane's WebContents may drive the bubble (`source` is checked against the
active pane, mirroring stock `UpdateTargetURL`'s anchor check). The bubble
re-anchors while visible on window move/resize (`OnWidgetBoundsChanged`) and
on a dock flip (`SetSidebarPosition` re-anchors it explicitly, since a dock
flip moves the card without changing window bounds). VLOGs log only
`GURL::host()`, never the full URL.

### Known limitations

| Limitation | Detail |
|---|---|
| Split-view anchor (v1) | Only the active pane's hovers show a bubble, and it anchors to the active pane's card bottom-left - not per-hovered-pane (same v1 choice as the load indicator) |
| Live retint | A tint change while the bubble is visible applies on its next show, not live |
| No status text / mouse avoidance | Only `SetURL`-driven behavior exists; `SetStatus`/`MouseMoved` have no Atrium equivalent (v1) |

## Sidebar position - right dock (todo batch 40-53)

Settings > Appearance > "Sidebar Position" docks the sidebar left (default)
or right, live for every open window - no relaunch. Persisted as
`settings.json`'s `sidebarPosition` (`"left"|"right"`, lenient decode:
missing or unrecognized reads left, `schemaVersion` stays 1).

ABI: `set_sidebar_position(host, position)` appended as the tail
`AtriumHostOps` field - standalone optional, NO dlsym group (the
`set_sidebar_width` posture: C++ always populates it, Swift nil-checks the
field). `position` decodes leniently in C++ too (anything not exactly
`"right"`, including NULL, reads left). Unlike per-window width it is
broadcast: a change pushes to every registered host
(`broadcastSidebarPosition`), and each new host gets a registration-time
push so a relaunch lands right-docked at first paint with no left flash.

What mirrors when right-docked:

- Content-card gutter hugs the docked side (`SetCollapsedContentInsets`).
- Hover-overlay reveal strip and slide-in/out move to the right window edge
  (`SetOnRight`).
- Cmd+S collapse slides the sidebar off the RIGHT edge.
- Resize handle moves to the sidebar's content-facing (left) edge, with the
  drag-delta sign flipped.
- The non-client hit-test band-controls carve is re-expressed as insets from
  the sidebar's content-facing edge, so the caption/drag regions mirror.

What does NOT mirror: the stoplights. They are native
`standardWindowButton`s pinned by AppKit to the window's top-left and never
move. While right-docked, the content card reserves the `kTitlebarHeight`
(40pt) top band as its top inset so the lights float over the tinted glass
band above the card, never over live web content - and collapse no longer
hides them (they belong to the card band, not the sidebar). The hover
overlay draws no stand-in lights while right-docked - the real ones stay
visible top-left.

| Condition | Effect |
|---|---|
| Degraded/old dylib (never calls `set_sidebar_position`) | Sidebar stays left regardless of `settings.json`, no crash |
| `settings.json` without the key / unknown value | Decodes clean, left default |
| Stale C++ build (no tail op) | Swift nil-checks the field; the Appearance picker persists but has no effect until a rebuilt chrome |

### Known limitations

| Limitation | Detail |
|---|---|
| Dock flip does not re-anchor an open peek card | `SetSidebarPosition` explicitly re-anchors the status bubble, but not a showing peek widget - it re-sizes on its next open or the next window bounds change (not yet fixed) |

## Profile display names

Users can rename how a profile shows up in Atrium's UI - DISPLAY NAME only,
never the directory basename (`Space.profileID`, still the identity key in
spaces.json/HostRegistry/RequiredProfilesJSON/per-profile favorites).
Source of truth is Chromium's own `ProfileAttributesStorage` (the entry
stock Chrome's profile picker reads/writes), not a new Atrium-owned file -
a degraded-launch stock picker and Atrium's own UI always agree on the name.

ABI: two fields appended to `AtriumHostOps` after `open_window_slot` -
standalone optional, NO dlsym group (the `set_sidebar_position`/
`open_window_slot` posture: C++ always populates both, Swift nil-checks
each).

- `copy_profile_names_json(host) -> char*` - a SYNCHRONOUS pull, the first
  `AtriumHostOps` field where SWIFT is the caller of a Copy-style ownership
  contract (Swift owns the buffer, must `free()` it - caller/callee reversed
  from `AtriumCopyRequiredProfilesJSON`). Returns
  `[{"id","displayName"}, ...]` for every profile `ProfileAttributesStorage`
  knows about. `host` is ABI symmetry only - the listing is global.
- `set_profile_display_name(host, profile_id, display_name)` - writes
  `profile_id`'s `ProfileAttributesEntry` local name via
  `SetLocalProfileName`. Validated through the SAME id-shape guard as every
  other cross-ABI profile id (`ProfileBootstrap::IsSafeProfileId`, promoted
  from `atrium_profile_bootstrap.mm`'s own anonymous namespace so this reuses
  it instead of a third drifting copy). Empty `display_name` resets to
  `profile_id` itself (marked a default name). Non-empty names are capped to
  64 UTF-16 code units.

Swift: `ProfileNamesStore` (process-wide cache, `AtriumState.profileNamesStore`,
lazily wired alongside spaces) - `displayName(for:)` never fails, always
falls back to the bare id. Pulled at every `registerHost` and again whenever
Settings opens (`openSettingsWindow`); `setDisplayName` writes through
immediately and updates the local cache with no echo to wait for. Consumers:
Settings > Workspaces pane's new "Profile Names" editable list (hidden
entirely when the ops never resolved - see the degradation matrix below),
the per-space `ProfileMenu`, and the Create Space form's profile picker -
all three show `displayName(for:)`, never the raw id, while still acting on
the id underneath. Left as raw ids (deliberately): the sidebar's
"Assign Profile..." free-text prompt (an edit target, not a display label)
and the browser-import mapping - it maps `profileID` verbatim with
no profile-picker UI to update.

### Degradation matrix

| Condition | Effect |
|---|---|
| Degraded/old dylib (fields absent) | `ProfileNamesStore.isAvailable` stays false; every display site falls back to the bare profileID; the Workspaces pane's "Profile Names" section hides entirely |
| Stale C++ build (fields resolve but chrome predates them) | Same as above - Swift's nil-check on either field is indistinguishable from "field absent" from Swift's side |
| Unknown/invalid `profile_id` passed to `set_profile_display_name` | Logged no-op in C++; no profile directory is created |
| Malformed/traversal-shaped id in `copy_profile_names_json`'s payload | Dropped by `ProfileBootstrap::IsSafeProfileId` (C++) and again by `ImportApplier.isValidProfileID` (Swift) before caching |

## Extensions

Extension toolbar actions - icons, badges, per-tab visibility, and the
install/uninstall/enable/disable/badge events - streamed from the profile's
`ToolbarActionsModel`/`ExtensionActionManager` to Swift. Seventh optional ABI
group, `extensions_connected_`, resolved the same AND-gated dlsym way as
`spaces_connected_`/`split_view_connected_`. CORE and every other group are
unaffected if it fails to resolve.

ABI: three `AtriumHostOps` ops appended after `set_auto_pip_enabled`
(`extension_action_click`, `open_extensions_page`, `uninstall_extension` -
Swift -> C++, populated unconditionally) plus two `@_cdecl` exports forming
the AND-gate: `AtriumOnExtensionActionsChanged(host, json)` (full-replace
snapshot for the active tab) and `AtriumOnExtensionActionIcon(host, id, png,
len)` (one icon, keyed by extension id process-wide).

C++ (`atrium_extension_bridge.{h,mm}`, built per host only when
`extensions_connected()`): observes `ToolbarActionsModel` and rebuilds the
whole snapshot on any observer event AND on tab activation / active-tab
navigation (a plain `OnToolbarActionUpdated` drops which `WebContents` it
affects, so C++ resolves badge/visible PER-TAB from the active WebContents'
session tab id and resends rather than diffing). Icons resolve async via a
per-extension `ExtensionActionIconFactory` (RAII map); `uninstall_extension`
is guarded by `ManagementPolicy::UserMayModifySettings`/`MustRemainInstalled`
(Swift confirms first - C++ is a pure executor). A `kShowPopup` click result
is VLOG-only.

| Condition | Effect |

| Degraded/old dylib (either export absent) | `extensions=0`; C++ never builds the extension bridge; no extensions pill/strip; the three ops are never called from Swift; no crash |
| Stale C++ build (dylib exports resolve but chrome predates the bridge) | No snapshots/icons ever pushed; Swift shows an empty extensions strip; everything else unaffected |
| Unknown/disabled extension id passed to any op | Logged no-op in C++ |

## Find in page

`Cmd+F` opens Atrium's find bar over the tab the window is showing. The bar is
the `/find` HTML surface, driven by Chromium's `FindTabHelper`.

- `Cmd+F`: Open the bar, or refocus it
- `Enter` / `Cmd+G`: Next match
- `Shift+Enter` / `Cmd+Shift+G`: Previous match
- `Escape`: Close, clear the highlights, return focus to the page

Not rebindable, and deliberately absent from `hotkeys.json`: these are stock
Chromium menu accelerators, not Atrium actions.

## Clean rebuild from scratch

    ./build/scripts/bootstrap.sh     # fetch chromium (once)
    git -C "$SRC" checkout $(grep '^chromium_tag=' build/VERSION | cut -d= -f2)
    make patches             # git am the numbered series -> branch atrium/<tag>
    make build

No manual chromium edits are ever needed - upstream changes live in
`patches/`, and the four owned roots live in `overlay/`.

## Patch model

The atrium chromium changes are a **git commit stack** on the checkout, branch
`atrium/<tag>`, exported as a numbered `git format-patch` series in `patches/`
(`0001-*.patch` ... one commit per subsystem). The old
cumulative `chrome-atrium.patch`/`m1-tabs.patch` blobs are gone; git history
keeps them.

`build/VERSION` pins the base (`chromium_tag`, `chromium_commit`) and records
the expected result (`atrium_tree` = the byte-exact tree hash the series must
reproduce, `patch_count`). `archive_tag` names the fork tag that keeps the
per-task commit history of the owned roots, which the series no longer carries.

| Command | Does |
|---|---|
| `make patches` | `git am` the series, then copies `overlay/` into the tree and commits it as `chore: add the atrium source overlay` |
| `make patches-regen` | Re-export `patches/` from the `atrium/<tag>` branch, with the owned roots excluded |
| `make patches-verify` | Drift guard: assert patches == branch == working tree == `atrium_tree`, and refuse any patch that touches an owned root |
| `make overlay-verify` | Drift guard: assert `overlay/` matches the four owned roots in the tree |
| `make overlay-sync` | Copy `overlay/` into the tree (repo -> tree), the normal direction after an overlay edit |
| `make overlay-adopt` | Copy the tree's owned roots back into `overlay/` (tree -> repo), the rescue for an edit made in the tree by mistake |

**Dev loop:** edit `overlay/` -> `make overlay-sync` -> build -> commit in
both repos. Run `make patches-regen` only when an upstream file changed. Run
`make patches-verify` before committing (wire it into a
pre-commit hook); it catches "working tree has changes not in the patches".

### ABI header sync (`atrium_bridge.h`)

Two copies of the ABI header must stay byte-identical - `$SRC/chrome/browser/ui/atrium/atrium_bridge.h`
(C++, canonical) and `swift/AtriumUI/Sources/AtriumBridgeC/include/atrium_bridge.h`
(Swift, a plain copy). C++ ahead of Swift is loud (Swift fails to compile);
Swift ahead of C++ is silent - Swift reads past the end of the
`AtriumHostOps` struct the built binary actually allocated.

| Command | Does |
|---|---|
| `make abi-verify` | Removed with the Swift package. There was a second copy of `atrium_bridge.h` under `swift/`, and this compared them. One copy cannot drift. |
| `make abi-sync` | Removed with the Swift package, same reason |

No Chromium checkout -> `abi-verify` warns and skips (exit 0) rather than
blocking a Swift-only build.

### Recovering the Swift arm

The hard cut deletes the whole Swift arm in one commit, and later
phases build on top of it, so it is not revertible in practice. The `last-swift`
tag is the way back.

```
make tag-swift          # move the tag; run after any Swift change and once before the cut
```

It tags BOTH repos, because the dylib and the Chromium tree that loads it are
two halves of one build. To recover:

```
source build/scripts/env.sh
git checkout last-swift                 # this repo
git -C "$SRC" checkout last-swift       # the Chromium tree
make build && make run
```

Neither tag is pushed. This is a local recovery point, not a release.

The tag refuses to move on a dirty tree, and refuses to run at all once
`swift/AtriumUI` is gone - after the cut it is a record, not something to
update.

### Model rules and the golden records

`docs/model-rules.md` holds the rules the Swift model layer keeps, each citing
the test it was read from. Those tests are deleted at the cut; the document,
and the three records below, are what the Rust core is built from.

| Record | Holds |
|---|---|
| `fixtures/stores/` | Real store files and the state each loads to |
| `fixtures/sidebar-model/` | The sidebar model JSON for five profiles |
| `build/generated/README.md` | Where every design token came from |

### Rust core sync (`atrium-core`)

The model core is a Rust crate with two copies, for the same reason the ABI
header has two: GN cannot build anything outside its own checkout.

| Copy | Role |
|---|---|
| `rust/atrium-core` | canonical - edit here, `cargo test` here |
| `$SRC/third_party/atrium/core` | a plain copy; GN builds this one |

C++ reaches the crate only through the hand-written
`include/atrium_core.h`. cbindgen is not vendored, so nothing generates that
header - every entry matches an `extern "C"` function by hand, and
`ATRIUM_CORE_ABI_VERSION` in the header must move with `ABI_VERSION` in
`src/lib.rs`. Two tests hold them together:
`atrium_core_abi_unittest.cc` compares the header's number against what the
linked library reports, and a `cargo test` case reads the header directly so
the check also runs without a Chromium checkout.

| Command | Does |
|---|---|
| `make rust-test` | The crate's own tests (no Chromium checkout needed) |
| `make rust-corpus` | Read the whole golden store corpus through the Rust core |
| `make rust-verify` | Drift guard: `diff -r` the two copies; also runs inside `make patches-verify` |
| `make rust-sync` | One-step fix: copy the repo crate over the Chromium copy |

Rust READS the persisted stores; Swift still writes them. `atrium_core_query`
takes a store name and the file's bytes and returns the loaded state as JSON,
and `atrium_core_sidebar_model` builds the sidebar document from a store file
plus the window's live tab strip.

**Nothing in the running browser calls either yet.** Swift cannot: the crate is
a GN target inside the Chromium tree and `swift/AtriumUI` is built by SwiftPM
outside it, with the host reaching the dylib through the ops vtable rather than
the other way round. Putting Rust on the live path needs a new host op, or the
model moving out of Swift. Until then the change is reverted by not calling it.

A file at a schema this build cannot read returns NULL, which is NOT the same
as empty defaults. Defaults look writable and are not - see
`docs/model-rules.md` R1.2.

`rust-sync` only runs repo -> tree. An edit made in the Chromium tree has to be
copied back by hand first, or `rust-sync` overwrites it.

The Rust toolchain comes with the Chromium checkout; nothing extra downloads.
`cargo test` uses whatever `cargo` is on PATH, which is a second toolchain -
the crate has no dependencies, so the two do not have to match.

## Pulling Chromium stable updates

Chromium stable releases are tags (`MAJOR.MINOR.BUILD.PATCH`) on the milestone
release branch. `build/scripts/update-chromium.sh` rebases the atrium stack onto a
newer tag:

| Step | Command | Automatable |
|---|---|---|
| Check | `make update-check` | yes (ChromiumDash; exit 10 = update available) |
| Rebase | `./build/scripts/update-chromium.sh start <newtag>` | fetch/branch/rebase yes; conflict resolution manual |
| Sync deps | `./build/scripts/update-chromium.sh sync` | yes (`gclient sync`) |
| Build/test | `make build && make rust-test` | compile fixes manual (`--fixup` into owning commit) |
| Finalize | `./build/scripts/update-chromium.sh finish <newtag>` | yes (re-export + bump VERSION + verify) |

Cadence: `make update-check` weekly (cron/CI). Take same-milestone bumps
promptly (security); schedule milestone jumps deliberately, one milestone at a
time. `rerere` is enabled on `start` so conflict resolutions replay across
bumps. Rollback at any point: `git -C "$SRC" rebase --abort` (the old
`atrium/<oldtag>` branch is never touched).

The maximum acceptable lag behind upstream stable, the SBOM (`make sbom`), and
the rest of the security-update pipeline this cadence feeds are in
`docs/SECURITY.md`.
